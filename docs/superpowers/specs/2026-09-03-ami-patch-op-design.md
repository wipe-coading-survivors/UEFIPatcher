# Спека: мини-цикл «ami-patch-op» — patch_ami пишет в payload-секции, записи переживают build_image

> Дизайн-документ, 2026-09-03. Статус: подход согласован с пользователем
> 2026-09-03 («научить patch_ami писать в payload-секции … плюс тест, который
> ищет записи именно в собранных байтах» — комментарий исследовательской
> сессии к BLOCKER-багу E17). Источник: TODO §«E17 → баг: patch_ami теряет
> записи при ребилде».

## 1. Контекст и проблема

E17 (formset add со схемой `setupdata_guid`/`amitse_guid`) собрал образ, в
котором файлы AMITSESetupData и AMITSE **байт-в-байт равны оригиналу** —
правки `patch_ami` не попали в собранные байты. Root cause:
`patch_ami` (`hii/ami_patcher.rs`) редактирует **body ФАЙЛА**
(`setupdata.body.extend_from_slice`, `amitse.body.splice`), но у реальных
файлов есть children-секции, и `build_file` (`builder/mod.rs:92-96`) при
Rebuild собирает body **из children** — правка файла выбрасывается.
Единственный путь выжить — писать в payload-**секцию** внутри файла
(как это делает `set_value` для NVAR-сторов).

Тот же тест-пробел: real-image приёмка formset_add проверяла рост PE-ресурса
HII-модуля, но не проверяла наличие AMI-записей в собранном образе.

## 2. Данные разведки (HNX99TF, побайтово, 2026-09-03)

| Модуль | Дерево движка | Payload |
|---|---|---|
| AMITSESetupData `FE612B72` (vi=3 fi=208, FV2) | File → GUIDed-LZMA(0x02, слот 0xC2C4) → секция **0x18** FREEFORM_SUBTYPE_GUID (body 0x77174) + UI | тело секции 0x18 = контейнер `"$SPF"` (AMITSE setupdata, aka $PFS) |
| AMITSE `B1DA0ADF` (vi=3 fi=206, FV2) | File → GUIDed-LZMA(0x02, слот 0x23878) → **PE32** (0x10, body 315264) + UI | тело PE32-секции |

Контейнер `"$SPF"`: body[0..16] = GUID секции, body[16..20] = сигнатура
`24 53 50 46`, далее блочная структура с таблицами смещений. Живые Table-3
записи (пробник value-op v3): **72 байта** (qid@0 u32, pageId@+12 u16,
access@+16, help-id@+20 u32, ifr-offset@+28 u32, prompt-id@+48 u32,
failsafe@+52, optimal@+53), например 4G-запись @body+0x99E8 (qid 0x3B,
access 0x09, help 0x01A4 / prompt 0x01A3).

## 3. Решение

`patch_ami` переписывается на адресацию payload-секций; формат записей и
семантика полей — **без изменений** (см. §6 «Не-цели»):

1. **setupdata-записи** → в $SPF-секцию. Поиск файла (как раньше: GUID →
   UI-имя → 108-маркеры), затем обход поддерева файла за leaf-секцией,
   чьё тело содержит сигнатуру `b"$SPF"` в первых 0x40 байтах. Записи
   аппендятся в **конец тела секции** (аддитивно: существующие блоки
   контейнера и абсолютные смещения внутри него не трогаются).
   Обёртка LZMA пересобирается билдером автоматически:
   `build_recompressed_guided` → `compress_lzma_fit(budget=слот)` —
   та же механика, что у `set_value` (E13/E14-рецепт).
2. **AMITSE-правки** → в PE32-секцию. Поиск файла → первая leaf-секция
   subtype 0x10; splice form-id записей у marker-позиции (байты 12..14
   GUID формсета; не найдена → конец тела секции) — прежняя семантика,
   новый адресат.
3. Обе правки: `mark_rebuild_to_root_by_path` от **пути payload-секции**
   (не файла) — Rebuild каскад поднимается через обёртку/файл/том.
4. **Precheck усиливается** (`precheck_ami_modules`): помимо файлов
   проверяется досягаемость обеих payload-секций (leaf за
   non-recompressable-обёрткой → `MutationBehindCompression`; не найдена →
   `AmiFilesNotFound`). Это сохраняет инвариант атомарности `c316da9`
   («после precheck у patch_ami нет Err-путей») — precheck в
   `add_setup_formset` выполняется до мутации строк.
5. Ошибки: payload-секция не найдена → `AmiFilesNotFound` (файл без
   payload для движка эквивалентен отсутствию AMI-модуля); за барьером
   Tiano/LZMAF86/COMPRESSION → `MutationBehindCompression`. Новых вариантов
   `HiiError` и изменений proto/CLI нет.

## 4. Приёмка

- **Unit**: синтетический образ (том → файлы → payload-секции):
  `patch_ami` → `build_image` → байты записей (SDP-запись + form-id
  пары) ищутся и находятся в **собранных** байтах; file-size/checksum
  пересчитаны (re-parse валиден).
- **Unit (LZMA)**: payload-секции за синтетической GUIDed-LZMA-обёрткой:
  после build recompressed-слот занимает исходный размер (slot-fit),
  записи видны в re-parse (дети материализуются декомпрессией).
- **Unit (барьер)**: Tiano-обёртка → `MutationBehindCompression`, дерево
  нетронуто; файл без payload-секции → `AmiFilesNotFound` через precheck
  ДО мутаций.
- **Real-image (HNX99TF, `#[ignore]`)**: `add_setup_formset` (схема с
  setupdata/amitse GUID) → `build_image` → re-parse: SDP-записи в теле
  $SPF-секции, form-id пары в PE32 AMITSE; длина flash сохранена;
  flash-дифф confined ровно к двум LZMA-слотам AMI-файлов
  (slot-fit паддинг `compress_lzma_fit`); вне-FV2 байты идентичны.

## 5. Риски и ограничения

- Слот LZMA: прирост декомпрессата ~108×N байт (записи почти нулевые)
  сжимается с запасом; переполнение слота не может произойти «молча» —
  `compress_lzma_fit` вернёт минимальный поток (рост секции), билдер
  честно пересоберёт файл, volume-pad удержит длину FV, а при исчерпании
  FV — `SizeMismatch` (явная ошибка).
- `find_formset_marker_position` по 2 байтам GUID[12..14] в PE32 —
  эвристика унаследована; для нового формсета маркер не встречается и
  записи аппендятся в конец (аддитивно).

## 6. Не-цели (явно за рамками цикла)

- **Формат SDP-записей**: текущий 108-байтовый writer НЕ соответствует
  живому Table-3 формату (72 байта, раскладка §2) и аппенд в хвост
  контейнера не регистрирует записи в блоках/таблицах $SPF — AMITSE их
  не прочитает. Это следующий цикл («$PFS-формат + TSE-видимость»,
  совместно с исследовательской сессией; требует HW-валидации E18).
  Данный цикл — исправление write-path: записи физически попадают в
  собранные байты и переживают rebuild.
- Парсер контейнера $SPF, page-таблицы, help/prompt-id и ifr-offset в
  записях — там же.
- Вставка записей внутрь существующих таблиц $SPF (сдвиг сломал бы
  абсолютные смещения контейнера — урок E9).
