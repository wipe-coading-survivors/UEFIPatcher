## 1. Контекст и проблема

Op `hii form hijack` (цикл page-hijack-op, E18) умеет: строковые
аппенды (en-US/bare + PE32-resource), same-length перезапись IFR
string-id (title/prompt/help), запись $SPF fs/opt. Серия E19–E26
доказала, что этого **недостаточно и частично вредно**:

- **E18-ловушка**: без unlock жертва невидима — сток-скрытая страница
  (suppress-if по NVRAM 0x9A/0x0A45) остаётся скрытой; результат op
  не наблюдаем. Unlock-механизм в движке уже есть (цикл unlock-op,
  `hii/gates.rs`, E12-валидирован), но hijack его не вызывает.
- **Хелп-канал**: IFR help-id ≠ источник хелпа. E26 доказал: хелп
  рендерится из **$SPF пул-контрола строк** (u16 str-id), которого op
  не знает.
- **Мёртвое**: fs/opt инертны (E23: образ без fs/opt ведёт себя
  идентично); IFR FORM title не рендерится нигде (подтверждено
  пользователем: шапка/пункт = сток 395 из $SPF title-id/goto).

## 2. Цели и не-цели

**Цели:**

1. `hii form hijack` v2 по полному рецепту: авто-unlock жертвы
   (u1) + строковые аппенды + IFR prompt/help + $SPF хелп-контрол.
2. Схема v2: `{"questions": [{"question_id", "prompt", "help"}]}`;
   title/failsafe/optimal удалены (u2), старый JSON отклоняется с
   понятной ошибкой.
3. Контракт: факт авто-unlock в RPC-ответе (+ warn в лог как
   страховка).
4. Верификация: real-image gate-тест (два сценария, §8) + E27 на
   железе (u3).

**Не-цели:**

- переименование страницы/пункта меню ($SPF title-id / goto ids —
  задокументировано в карте каналов, не реализуется);
- аппенды в x-AMI пакет (гипотеза закрыта E21);
- регистрация новых страниц (§4 разведки — отдельный будущий цикл);
- обобщение за пределы AMI-сигнатур (op остаётся AMI-специфичной,
  как и текущий hijack).

## 3. Каналы рендера и байтовые мишени (источник истины)

Карта каналов (все hardware-доказаны; полная летопись — TODO.md
секция 455, сводка — recon-отчёт §9):

| Канал | Источник | Мишень правки |
|---|---|---|
| видимость страницы | suppress-if вокруг FORM/REF | флип литерала гейта (gates-слой) |
| видимость вопроса | grayout-if вокруг вопроса | флип литерала гейта (gates-слой) |
| prompt вопроса | IFR prompt-id | u16 @ q_off+2 |
| help вопроса | $SPF запись s14 **и** пул-контрол str-id (обе копии; E27/E28) | u16 s14@+0x14 записи + u16 str-id@+2 контроля |
| опции one_of | сток IFR | не трогаем |
| пункт меню / шапка | goto / $SPF title-id (395) | не трогаем |

Ориентиры на живом образе (форма 10029, вопрос q59): unlock жертвы =
3 байта (dec 0x8FB2: 01→02 — REF-гейт; dec 0x9709-0x970A: 0100→FFFF
— grayout q59, паттерн `19 82 12 06 9a 00 01 00`); полный unlock
страницы (E25) = +9× FFFF + 1× 0x0A45-константа. Хелп-контрол q59:
str-id @0x5106 (body-relative $SPF-контейнера), сток 420. Точные
списки флипов gate-тест фиксирует по диффам эталонов.

## 4. Отклонённые альтернативы

- **Вызов `pub unlock()` как чёрного ящика на каждую жертву**:
  дублирует флипы общих гейтов, ломает атомарность (unlock мутирует
  до строковых precheck'ов, `mark_rebuild` выполняется дважды).
  Вместо этого hijack вызывает `find_gates`/`plan_gates`/`apply_flips`
  напрямую.
- **Полный парсер пула $SPF-структур** (страницы→контролы): 70/187
  страниц имеют off-by-4 квирк, связи страница→контрол декодированы
  не полностью — рискованно и не нужно; сигнатурного скана достаточно.
- **`--unlock minimal|full|none`**: дублирует семантику unlock-op;
  отклонено при брейнсторме (u1).

## 5. Операция: пайплайн и атомарность

`hijack_form` v2, все проверки до первой мутации (всё-или-ничего,
как сейчас):

1. **Precheck** (существующее): Write-режим; форма `<target>#<form>`
   существует; все вопросы схемы есть в форме; путь без
   непреcompressible-секций.
2. **Precheck unlock**: планирование флипов gates-слоем на IFR-пакете
   формы. Два класса `GateTarget` (семантика `find_gates`):
   `{form_id, None}` — suppress вокруг самой FORM и всех REF→form_id;
   `{form_id, Some(qid)}` — grayout вокруг каждого вопроса схемы.
   Флипы сливаются и дедуплицируются по offset. Гейт не сводится к
   E12-классу → отказ всей op с диагностикой
   (`GateExpressionUnsupported`), как в unlock-op.
   **Важно (найдено при ревью кода):** текущий `plan_gates` считает
   уже-вскрытый гейт ошибкой («not a hardware-validated flip class»:
   `EqConst` с `a≠b` и `EqIdVal` с `value==0xFFFF` не матчатся
   охранами `plan_flip`). Для hijack это ломает и повторный запуск, и
   сценарий B (unlock до hijack). Поэтому в gates-слое добавляется
   идемпотентный планировщик `plan_gates_skip_unlocked`: уже-вскрытые
   классы → пропуск (без флипа и без ошибки), нераспознанные → та же
   ошибка, что в `plan_gates`. Semantics самого `unlock` op не
   меняется (его неидемпотентность — отдельная запись в TODO).
3. **Precheck $SPF**: файл SetupData найден; на каждый вопрос — ровно
   одна f8-запись в IFR-спане формы (существующий корреляционный
   гейт, теперь только чтение); снимок текущих IFR help-id вопросов;
   сигнатурный скан контролов — на каждый help-id ровно один контроль
   (§6), иначе отказ с диагностикой.
4. **Применение**: строковые аппенды → IFR-правки prompt/help
   (титул формы не трогаем) → unlock-флипы → u16 str-id
   хелп-контролов → новый help-id. `mark_rebuild_to_root` по каждому
   затронутому пути (Setup-модуль; SetupData).
5. **Результат**: `HijackResult` v2 (§7) + `tracing::warn!` со
   сводкой авто-unlock (страховка u1).

Идемпотентность повторного запуска обеспечивается тремя механизмами:
`plan_gates_skip_unlocked` (гейты, вскрытые прошлым запуском,
пропускаются); локатор хелп-контролов ищет по **текущему** IFR help-id
(после первого прогона — уже аппенднутый id), находит и перезаписывает
корректно; строковые аппенды добавляют новые id.

## 6. Сканер $SPF хелп-контролов (`hii/spf.rs`)

Факты с реального контейнера (HNX99TF, body-relative): в пуле
структур — лестница из 11 контролов (str-id 411–421, stride 0x108),
каждый:

```
{u16 5 @+0, u16 str-id @+2, u16 0 @+4, u16 idxA @+6,
 u16 idxB @+8, u16 78 @+0xA, zeros, u32 57 @+0x14, u32 ptrs[]}
```

- Сканер: `scan_string_controls(body) -> Vec<SpfStringControl{offset,
  string_id}>` — проверка полей +0/+4/+0xA (u16 5 / 0 / 78); на
  реальном образе 11 хитов, ложных срабатываний нет (старые ложные
  «хиты» 419/420 были у наивного u16-поиска без сигнатуры).
- `SpfStringControl.offset` — адрес поля str-id (контрол+2).
- Правка: 2 байта str-id, длины не меняются; слот-фит и LZMA-ребилд —
  существующий путь билдера.
- Правило ровно-одного матча на вопрос: 0 или ≥2 → отказ op с
  диагностикой (help-канал непокрыт/неоднозначен).
- Для hijack патчится **только help-контроль** вопроса; prompt-контроль
  (лестница содержит и prompt-копии) не трогаем — E24/E26 доказали,
  prompt рендерится из IFR при сток-контроле.

## 7. Контракт и схема v2

- Схема `--file` (строгая, лишние поля — ошибка валидации с перечнем
  допустимых):

```json
{"questions": [{"question_id": 59, "prompt": "…", "help": "…"}]}
```

- `HijackResult` v2: `string_ids` (как было), `unlock_flips:
  Vec<String>` (тексты в формате `flip_text` unlock-op), 
  `help_controls: Vec<{question_id, offset, old_string_id,
  new_string_id}>`; `records` (fs/opt) и перезапись title удалены.
- Риппл: `uefi-proto` (тип ответа), `uefi-cli` (вывод), mock-серверы
  CLI/TUI/gateway. Команда CLI неизменна:
  `uefi-cli hii form hijack --target <t>#<form> --file …
  --setupdata-guid …`.

## 8. Тестирование и верификация

- **Юнит (TDD)**: сканер контролов на синтетическом контейнере
  (лестница сигнатур; кейс «два матча → отказ», «ноль → отказ»);
  `plan_gates_skip_unlocked` (уже-вскрытый `EqConst`/`EqIdVal` →
  пустой план; нераспознанный → ошибка); дедупликация флипов двух
  таргет-классов; идемпотентность повторного hijack; валидация схемы
  v2 (старый JSON с title/failsafe → ошибка с диагностикой);
  атомарность — отсутствие мутаций при отказе на каждом новом
  precheck-классе.
- **Real-image gate** (`crates/uefi-engine/tests/real_image.rs`,
  `#[ignore]`, живой образ HNX):
  - сценарий A (hijack без отдельного unlock): флипы = ровно 3 байта
    E24-класса (REF-гейт + grayout q59); IFR prompt/help → аппенднутые
    id, title формы не тронут (остаётся сток); хелп-контрол q59
    str-id → новый help-id; дифф образа confined в слоты Setup и
    SetupData.
  - сценарий B (unlock страницы + hijack): `hii form unlock
    #10029` + `hii question unlock` остальных вопросов + hijack →
    суммарные флипы соответствуют полному набору E25/E26; контент
    $SPF-контейнера отличается от оригинала только флипами,
    str-id хелп-контрола и ожидаемыми полями.
- **E27 на железе** (u3): чисто движковый образ — ожидание = состояние
  E26: полная страница PCI Subsystem Settings, у q59 наш prompt и наш
  help, опции Enabled/Disabled, значения сохраняются в NVRAM.
  Команды сборки (полный сценарий B):

```
uefi-cli session init --name e27 --force
uefi-cli image open refs/fw/HNX99TF_200525_original_E5C88C6F.bin --mode write
uefi-cli hii form unlock --target 899407d7-99fe-43d8-9a21-79ec328cac21:0x10:0#10029
# вопрос q59 вскроет сам hijack; остальные вопросы страницы:
uefi-cli hii question unlock --target …#10029:<qid>   # для каждого q54–q61, qid≠59
uefi-cli hii form hijack \
  --target 899407d7-99fe-43d8-9a21-79ec328cac21:0x10:0#10029 \
  --file /tmp/e27-schema.json \
  --setupdata-guid FE612B72-203C-47B1-8560-A66D946EB371
uefi-cli image save refs/amibcp/e27-hijack-v2-engine.bin
```

## 9. Риски и открытые вопросы

- **Сигнатура контролов — AMI-специфична** (лестница HNX). На другом
  вендоре/плате: 0 матчей → явный отказ с диагностикой; деградации
  молча нет. При будущей встрече с другой раскладкой — расширение
  сканера отдельным циклом.
- **Количество флипов полного unlock** (9× FFFF против 8 вопросов и
  вторая 0x0A45-точка) — движок берёт фактические гейты из IFR;
  gate-тест пинит точный список по диффам эталонов, расхождение = баг.
- **LZMA-ребилд обоих слотов** — уже hardware-доказан (E12/E18);
  новых механик сжатия в цикле нет.


## 10. Аддендум (2026-09-05): хелп-канал = ДВЕ копии id, E27/E28

E27 (движковый, s14=сток, контрол=наш) — хелп сток; E28 (E27 + 2
байта s14→750) — хелп наш. Вместе с E25/E26: хелп наш только когда
ОБЕ копии help-id в $SPF (запись s14 @+0x14 и пул-контрол str-id)
указывают на аппенднутый id. Следствие для op: стадия записи s14
возвращается в hijack (v2.1); fs/opt по-прежнему мертвы и не
возвращаются. Контракт дополняется help_records.
