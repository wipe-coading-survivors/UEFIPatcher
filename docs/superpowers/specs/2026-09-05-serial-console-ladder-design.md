# Serial Console Ladder — umbrella-спека дуги S0–S5

Дата: 2026-09-05. Статус: утверждён подход (лестница доказательств),
первая ступень — S0. Живой документ: ступени уточняются аддендумами,
как hijack-v2 → v2.1.

## 1. Цель дуги

Полный AMI-функционал serial-консоли на HNX99TF (HNX99TF_200525,
E5C88C6F): вывод загрузки UEFI на COM-порт **и** redirect самого
Setup-экрана (AMI Console Redirection), с настройками в Setup. Ос-часть
(GRUB/Linux на UART) уже работает у владельца — задача покрывает только
UEFI-слой. Формулировка цели — `user-input.md` п.1 (../../PLAENING/
UEFIPatcher/user-input.md, строка 7).

Конечный артефакт каждой ступени — образ, собранный движком UEFIPatcher,
прошитый и валидированный на железе (конвенция E-серии).

Целевой исход — полный AMI-функционал (настройки term/serialio в Setup
+ boot-вывод + redirect Setup-экрана). Допустимая полумера на случай
краха целевого решения (решение владельца, не план по умолчанию):
edk2-пара Term/Serial **без** настройки их параметров из Setup, но с
видимым и работоспособным Setup-экраном на serial-терминале — «как
через стандартную консоль». Владелец рассчитывает на целевое решение
(«осилим»); полумера — аварийный план, а не сокращение цели.

## 2. Отправная точка (что известно на 2026-09-05)

### 2.1 Доказано движком и железом (цикл hijack-v2 + v2.1, E26–E29)

Карта каналов рендера Setup (6/6): видимость, prompt, help (обе копии

| LEGACYREDIR | 4A3602BC-1A05-4C82-99B4-588CD2A32CD5 | C275D4I3.20@0x2AAA48, rd450x@0x8F8E80, x99runing@0x8E7450, MNX99MR9A@0x8E6D18 |
| SerialMiuxControl | 129F6AA7-AB69-4CB8-AED1-40985001115E | C275D4I3.20, rd450x |
| Terminal (edk2-имя) | 7A08CB98-E9BC-41C3-BE19-B302F3F1F595 | заявлен в «226», сырым сканом не найден (вероятно в сжатом FV) |

rd450x = `refs/amibcp/450x-4g-default.bin` (+ копия). Полные доноры в
`/var/home/dsevosty/downloads/bios/HNX99TF_200525_kot/` (MNX99MR9A,
JYX99D4, x99runing, v011). В живом HNX99TF (E5C88C6F) пары
TermSrc/SerialIo нет вовсе.

Факты по модулям: оба — FFS type 0x07 (DXE_DRIVER), payload в LZMA
guided-секции **EE4E5898-3914-4259-9D6E-DC7BD79403CF** — родной GUID
движка (`ffs.rs` lzma_guid), т.е. insert/rebuild без нового кода
компрессии. SerialIo имеет явный DXE DEPEX =
`PUSH(13A3F0F6-264A-3EF0-F2E0-DEC512342F34)` = gEfiPcdProtocolGuid.
TermSrc — без явного DEPEX. PE32 обоих почти без строк (конфиг через
PCD/переменные, не через строки).

**Корневые `TerminalSrc.ffs`/`SerialIo.ffs` (downloads/kot) — не те же
сборки, что UEFITool-экстракты из MNX99MR9A** (S0-уточление R24–R26,
отчёт §4.4/§6.3): SerialIo-пара различается на ~9 КБ (8 975 Б), дифф
размазан по всему .text — 301 регион при равной длине PE32
14 816 = 14 816; TerminalSrc-пара — другой билд, +320 Б PE32 (38 240 vs
37 920; «38244 vs 37924» — UEFITool-конвенция, включает +4 Б заголовка
секции). KOT-root — не «переобёрнутые FFS», а другие билды PE32 (штамп
имени модуля в PE+0x40; +80/+15 Б FFS — лишь LZMA-перепаковка иного
кода). История «кривых» — в разнобое сборок.
**Эталонный донор — rd450x** (решение владельца): пара модулей лежит
смежно (TermSrc@0x981EE0, SerialIO@0x985318), там же SerialMiuxControl
и LEGACYREDIR. MNX99MR9A — второй донор и источник IFR-дампа меню
(§2.4). Примечание: «Terminal» 7A08CB98 из «226» сырым сканом не
находится нигде — вероятно внутри сжатого FV донора; в S0 распаковать
сжатые тома доноров и пересканировать. Конечное решение по бинарям —
за S0/S4.

### 2.3 Прошлые попытки (все неудачны: консоль молчала, меню не было)

Архив попыток владельца: `~/git/BIOS` (112 файлов) — по именам читается
хронология: `HUANAN-mod-CR-*` (CR = Console Redirection), варианты
`TerminalScr-SerialIo-modified_body3/4`, серия `try3/try6`,
`CR_HII_module_F46A2D22.ffs`, `build_ffs.py`, донор-референсы
(`ASUS-setup-test-pe.rom`). Полная инвентаризация по именам+датам и
реконструкция «что меняла каждая попытка» — S0.1 (прецедент: прошлая
инвентаризация триггернула серию мини-циклов).

`huananx99tf-serial.rom` = v011_5B7C6A7F + ровно одна вставка 25 294 Б
@0xB23E08 (оба модуля в свободное место). Больше изменений нет: ни
Setup, ни NVRAM, ни регистрации страниц, ни LEGACYREDIR. Меню
структурно появиться не могло. Отдельный жёсткий факт прошлых попыток:
**свободного места не хватало катастрофически** — ради вместимости
приходилось удалять хелп-строки (безуспешно). Аудит свободного места
всех FV живого образа — первоочередной пункт S0.1, вместимость —
ограничение первого класса для всей дуги.

Причины молчания — гипотезы на проверку
в S0: (а) вставка вне диспетчеризуемого FV; (б) донорские модули читают
PCD-токены чужой PCD-базы (DEPEX = PCD-протокол) и не находят их;
(в) `SerialPortsEnabledVar` и Setup-оффсеты не инициализированы;
(г) консоль не маршрутизирована в ConOut; (д) гипотеза владельца:
«кривые» — потому что пишут по «кастомным» NVRAM-адресам
(оффсеты/переменные, которых на нашей плате нет) — частный случай
(б)/(в), проверка в S0.4.

### 2.4 Меню-референс (донорский Mashinist IFR)

`mashinist_setup.sct.fbd.0.0.en-US.uefi.ifr.txt`: форма 0x2722
«Serial Port 1 Configuration» (COMA, CheckBox q0x35, VarStoreId 0x14),
форма 0x272C «Serial Port Console Redirection» + дочерние 0x272D (EMS),
0x272E (Legacy Redirection Settings), 0x272F (Console Redirection
Settings: Terminal Type q0x59, Bits per second q0x5A, Stop Bits …).
Карта varstore донора (полная, из заголовка IFR-дампа):

- основной `Setup` (0x1, GUID EC87D643, 0x7D Б) — display-настройки
  редиректа (оффсеты 0x31–0x46); лэйаут у HNX99TF другой — порт
  вопросов «как есть» невозможен;
- VarStoreId 0x14 = **`PNP0501_0_NV`** (3 Б) — PNP0501 = ACPI PnP-ID
  16550 UART: сюда пишет CheckBox «Serial Port (COM)» (COMA enable);
- вся serial-семья под одним GUID **560BF58A-1E0D-4D7E-953F-2980A261E031**:
  PNP0501_0_VV/NV и PNP0501_1_VV/NV (COM1/COM2 volatile/non-volatile,
  0x13–0x16), PNP0510_0_VV/NV (0x11/0x12), `SerialPortsEnabledVar`
  (0x18); отдельно `DebuggerSerialPortsEnabledVar` (0x19, 97CA1A5B-…);
- `NCT5532D_SMF` (0x17, 2634D36A-…) — SuperIO донора Nuvoton NCT5532D;
  SIO чип HNX99TF — выяснить в S0 (если совпадает/совместим — шансы
  донорского SerialIo резко выше);
- `AMITSESetup` (0x6, C811FA38-…) — настройки самого TSE: кандидат на
  канал включения redirect для S5.

## 3. Лестница S0–S5

Принцип: каждая ступень заканчивается железным доказательством (или,
для S0/S1, детерминированным артефактом); следующая ступень не
начинается, пока предыдущая не закрыта. Ступень, разрастаясь, уточняет
эту спеку аддендумом.

Процессный принцип **pre-check** (перенесён владельцем из
параллельного проекта; здесь уже обкатан питон-скриптами разведки,
из которых выросли E-минициклы): план каждой ступени пишется только
после её pre-check'а — короткой разведки, закрывающей развилки, с
отчётом. S0 целиком = pre-check дуги; ступени S2+ при появлении новых
развилок открываются своим мини-pre-check'ом (мини-S0) и лишь затем
получают план.

  вставки 0xB23E08 в v011: какому FV принадлежит свободное место,
  диспетчеризуется ли этот FV (PEI-apriori/Bds перечисление); аудит
  свободного места всех FV образа E5C88C6F (урок: хелп-строки ради

- S0.5: легаси-слой: роль LEGACYREDIR и SerialMiuxControl (в каких

### S1 — Сборочная инфраструктура edk2

`docker/edk2-builder.containerfile` на базе `runtime-base.containerfile`
(наследование через наш общий базовый образ — однотипность; edk2
toolchain поверх), стендовая сборка SerialDxe + TerminalDxe (fixed PCD:
0x3F8, 115200, 8N1; glue для ConOut — нужен: вставка пары без glue

воспроизводимая
сборка в контейнере; .ffs-артефакты коммитятся как тест-данные (это не
BIOS-образы, исключение из «refs не коммитим» не требуется — кладём в
`crates/uefi-engine/tests/data/`).

### S2 — Говорящий UART (флеш-гейт E30)

`edit insert` собранных .ffs в живой образ E5C88C6F в целевой FV (из
S0) + NVRAM-инициализация, если разведка скажет. Гейт: UART-адаптер
видит UEFI boot-вывод. Доказывает: выбор FV, диспетчеризация, 16550,
маршрут консоли.

### S3 — Настройки в Setup

Пункты serial-настроек в Setup (enable/baud/terminal type) механикой
hijack/append; varstore — новая именованная переменная или свободное
место варстора Setup (решение — по итогам S0.2); драйверы читают
переменную (пересборка S1-пары на чтение переменной). Гейт: пункты
видимы, смена baud меняет скорость на COM.

### S4 — AMI-стек: TermSrc+SerialIo с починенной привязкой

По вердикту S0.4 — один из трёх путей: (а) бинарный патч PCD-токенов
донорского бинаря под нашу PCD-базу и/или инициализация
`SerialPortsEnabledVar`/`PNP0501_0_NV`+Setup-оффсетов; (б) наши
собственные собранные драйверы, адаптированные под Huanan (расширение
S1-пары до нужного функционала — компиляция против локальных
фиксированных настроек платы); (в) гибрид (донорский TermSrc поверх
нашего SerialIo или наоборот). Гейт: AMI-консоль работает.

### S5 — Redirect Setup-экрана (полный AMI)

LEGACYREDIR (+SerialMiuxControl при необходимости) + включение
redirect-политики AMITSE (переменные, возможно вскрытие его опций).
Финальный гейт: Setup-экран на терминале, управление с терминала.

## 6. Риски (верхнего уровня)

- **PCD-разрыв** (донор ↔ наша сборка) — центральный риск S4; лестница
  построена так, что S2–S3 от него не зависят (edk2-пара с fixed PCD).
- **AMITSE-политика**: redirect Setup-экрана может требовать больше,
  чем переменные (модификация самого AMITSE) — тогда S5 уточняется
  аддендумом; крайний случай — переход на допустимую полумеру из §1
  (edk2-пара с видимым/работоспособным Setup-экраном на терминале без
  настройки параметров из Setup).
- **Разрастание ступеней** — ожидаемо и принято владельцем: ступени
  уточняются, порядок не меняется без решения владельца.

## 7. Решения S0 (аддендум)

S0 закрыта 2026-09-05: отчёт `docs/reports/2026-09-05-serial-s0-recon.md`
(решения — §8, вердикты гипотез — §8.4).

- **Целевой FV S2**: FV1 (DXE) @0x890000, name 5C60F367-…, append в
  свободный хвост (первый слот 0xB63B18); free_tail 2 082 028 Б ≈ 99×
  потребности; все прошлые попытки вставляли туда же (отчёт §2, §8.1).
- **Конфиг edk2-пары** (вход S1): модули SerialDxe 9A5163E7 +
  TerminalDxe 9E863906 + glue (нужен: в LIVE нет терминального
  консьюмера SerialIo и edk2-консольного стека). PCD: все дефолты годны
  (= COM1 0x3F8/115200/8N1), единственная правка
  `PcdDefaultTerminalType=3` (VT-UTF8). Glue-развилка — (а)
  UpdateConsoleVariable до BDS / (б) gST->ConOut в ReadyToBoot / (в)
  полный ConPlatform+ConSplitter — решение за планом S1 (отчёт §5.3-4,
  §8.2).
- **Путь S4**: (б) своя сборка — основной; (а) бинарный патч донора —
  резерв (SerialIo патчей не требует: SIO-семейство совпало, привязка
  к детям GenericSio/AmiSio; TermSrc — размер Setup→0x72, CR-оффсеты,
  +2–3 NVRAM-записи); (в) гибрид только «донорский SerialIo + наш
  TerminalDxe» (отчёт §6.5, §8.3).
- **Гипотезы §2.3**: (а) опровергнута (вставка была в диспетчеризуемый
  FV1); (б) опровергнута (PCD — только DEPEX-гейт; конфиг пары =
  NVRAM-переменные + SIO-протоколы); (в) подтверждена (три TermSrc-
  переменные в LIVE отсутствуют, Setup-лэйауты чужие); (г) подтверждена
  для edk2-пары (нет консьюмера/маршрута в ConOut); (д) частично —
  семья инициализирована фабрично (PNP0501_0_NV=01 00 00), но
  «переменных/оффсетов нашей платы нет» — подтверждено (= (в)). Молчание
  — свойство E5C88C6F-эры; v011+пара давала мусорный вывод (порт
  работал).
- **Уточнённые unknowns**: S3 — геометрия $SPF переносима (zero-slot +
  bump, эталон MNX99MR9A с полным семейством форм; плато-поля копировать
  с LIVE; новых varstore не вводить — семья 560BF58A уже в IFR и
  включена); S5 — легаси-трое (LEGACYREDIR/SerialMiuxControl/
  SerialRcovery) не нужны, AMITSE включать нечего; риск — CsmDxe
  отбирает UART при CSM-буте (активность CSM не установлена — мини-pre-
