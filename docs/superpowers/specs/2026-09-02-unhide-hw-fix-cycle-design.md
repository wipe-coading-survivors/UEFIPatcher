# Спека: цикл фиксов по аппаратной валидации unhide (HNX99TF)

> Дизайн-документ, 2026-09-02. Статус: дизайн утверждён пользователем
> (brainstorm-цикл 2026-09-02: полный мини-цикл, все три минора, финальная
> HW-фаза, подход 1 — liblzma + raw-LZMA). Источник: секция TODO
> «Аппаратная валидация unhide на Huananzhi X99-TF (2026-09-02)» и отчёт
> `docs/reports/2026-09-02-hw-validation-hnx99tf.md` (§3 корневые причины,
> §7 открытые пункты). Пробники и E-образы: `refs/amibcp/` (вне репо).

## 1. Контекст и проблема

Аппаратная валидация 2026-09-02 (живая прошивка программатором, матрица
E1/E3/E5/E6/E7) изолировала два корневых дефекта движка и одну ошибку
обхода:

1. **LZMA-поток lzma-rs валит плату.** Движковая рекомпрессия
   (`compress_lzma`, `compress.rs:14`) даёт поток класса lzma-rs —
   POST идёт, но видеописк «нет видеокарты». Дифференциальная цепочка:
   E1 (lzma-rs + сдвиг) мёртв; E6 (чистый сдвиг того же объёма, родной
   поток) жив; E3/E7 (liblzma-потоки, разные раскладки) живы. Класс
   потока — единственный объясняющий фактор (все прочие байты E1
   проверены попарно).
2. **Пустые подписи раскрытой формы = нет PRC-токенов.** Форма 901
   «CPU HWPM State Control» после unhide открывается, но виджеты без
   подписей: строки 4894/4965/4969 есть в display-пакете `en-US`, а в
   токен-пакете `x-UEFI-AMI` (AMI-токены `PRC0003`/`PRC11B`/…) записей
   для них нет — вендор не создавал токи для скрытой формы. Корреляция
   полная: у каждой отрендеренной строки видимых форм PRC-запись есть.
3. **`hii string list` отдаёт только первый string-пакет** — 16 строк
   вместо ~5.7k на HNX99TF: `walk_for_string_package`
   (`strings.rs:236-258`) останавливается на первом непустом пакете.
   Полная карта строк — предпосылка PRC-патчинга.

Плюс три минора сессии: +2/+1 хвостовые байты билдера (засоряют дифф),
`ops::rebuild` не принимает GuidSection-таргеты, artifact export пишется
в CWD движка.

## 2. Цели и не-цели

**Цели:**

1. Кодировщик liblzma-класса: raw-LZMA1 + собственный 13-байтовый
   alone-заголовок с точным size, параметризация lc/lp/pb/dict/nice/mf,
   свип с приоритетом вписывания в исходный слот секции (минимальный
   дифф E3-стиля).
2. `collect_strings` — полный обход всех string-пакетов всех HII-файлов
   (bare-секции + PE-resource-каналы); внутренний API перечисления
   пакетов для PRC-логики.
3. `string_pack` — вставка SIBT-записей на конкретные id (разрезание
   SKIP-пропусков) для body- и resource-каналов.
4. `set_item_visibility` — автоматический PRC-патч строк раскрытой
   формы (генерация недостающих токенов `x-UEFI-AMI`) с pre-check
   атомарности.
5. Миноры: хвостовые байты билдера; GuidSection-таргеты `ops::rebuild`;
   artifact export по CWD клиента.
6. Real-image acceptance на HNX99TF + финальная живая прошивка
   образа-кандидата (пользователь) с чеклистом: POST, видео, форма 901
   с подписями.

**Не-цели:**

- Перенос PRC-патча в TUI/WebUI (клиентов у RPC нет; CLI не расширяется).
- Реверс-инжиниринг формата AMITSE: механизм «нет токена → пустая
  подпись» принимается как эмпирический факт; каузальность подтверждает
  финальная HW-проверка.
- Рекомпрессия Tiano/F86/COMPRESSION-0x01 (без изменений, спека
  `2026-08-14-lzma-recompression-design.md`).
- Компактфикация STRING-пакетов, «семантический diff», PE-checksum —
  повестка отдельного брейнсторма (TODO «последствия решения B»).
- Замена декодера: `lzma-rs` остаётся декодером в `decompress.rs`
  (AMI/liblzma/lzma-rs потоки декодирует корректно — проверено
  живыми образами и E-матрицей).

## 3. Верификационные данные

Из отчёта `2026-09-02-hw-validation-hnx99tf.md` и пробников
`refs/amibcp/probes/`:

- **Живые потоки**: оригинал AMI — props 0x5D (lc3/pb2), dict 16 МиБ;
  liblzma E3/E7 — props 0x00 (lc0/lp0/pb0), dict 16 МиБ, MF_BT4,
  nice 273, size в заголовке, хвост слота добит нулями. Декодер
  останавливается по заявленному size — техника прошита и жива.
- **Сжатие лучше AMI**: pb0/lc0 на движковом контенте даёт файл
  0x1611B против родных 0x16279 (слот секции 0x161a1) — вписывание
  в исходный слот достижимо уже дефолтной точкой свипа.
- **PRC-структура**: у HII-файла ABBCE13D в одном package-list два
  STRING-пакета: `en-US` (display) и `x-UEFI-AMI` (токены). Формат
  записей токен-пакета — стандартный SIBT (reader `hii/strings.rs`
  его уже читает); точный вид блоков (SCSU/UCS2) сверить по
  извлечённым данным пробников на первом шаге плана.
- **Рост .rsrc валиден на железе**: E7 (движковая раскладка с ростом,
  liblzma) грузится; reloc-aware рост отработан формсетами (спека
  `2026-08-14-hii-form-addition-design.md`, фаза B).
- **Сдвиг невиновен**: E6 (чистый сдвиг +0x2C0A8) грузится — байтовая
  раскладка не является фактором риска, класс потока — является.

## 4. Дизайн

### 4.1 LZMA-кодировщик + slot-fit

**Зависимость.** Крейт `liblzma` (поддерживаемое продолжение xz2;
системная liblzma через liblzma-sys) в workspace и `uefi-engine`.
`docker/rust-builder.containerfile` получает `xz-devel` (альтернатива —
static-фича крейта; выбрать по контейнеру на шаге плана). Первый шаг
плана — API-проверка: биндинг должен экспонировать параметры lc/lp/pb
raw-LZMA1-энкодера; если нет — прямой вызов `liblzma-sys`
(`lzma_raw_encoder` с полной `lzma_options_lzma`), это тот же
биндинг-пакет, не новая зависимость.

**Кодировщик** (`compress.rs`):

- `LzmaEncodeParams { lc, lp, pb, dict_size, nice_len, mf }`; дефолты:
  lc0/lp0/pb0, dict 16 МиБ, MF_BT4, nice_len 273.
- Поток: raw-LZMA1-энкодер; заголовок собирается вручную (13 байт):
  props-байт `(pb*5 + lp)*9 + lc`, dict-size u32 LE, unpacked size
  u64 LE (точный). Хвост за потоком в слоте — нули.
- `compress_lzma(input)` сохраняет сигнатуру и семантику для внешних
  вызовов и тестов; внутри — дефолтные параметры; round-trip-проверка
  через `decompress::decompress` остаётся.
- `compress_lzma_fit(input, budget: Option<usize>) -> Vec<u8>`: свип
  сетки pb∈0..=2 × lc∈0..=4 × lp=0 (lc+lp≤4), старт с pb0/lc0; при
  наличии budget — ранний выход на первом влезающем кандидате,
  возврат — поток, добитый нулями до budget; иначе — минимальный по
  размеру кандидат. Выбранный кандидат проходит round-trip-проверку.

**Интеграция в билдер** (`build_recompressed_guided`,
`builder/mod.rs:162-185`): budget = исходная длина потока
(`node.body.len() - prefix_len`). Влезли — размер секции/файла не
меняется (set_section_size даёт исходный total, файлы не сдвигаются,
pad-file-механика не участвует) — дифф E3-стиля. Не влезли — текущая
раскладка роста (E7-стиль, валидна на железе).

### 4.2 Полный обход строк

`hii/strings.rs`:

- `walk_for_string_package` → полный обход без ранних `return`:
  все bare string-package секции **и** все STRING-пакеты всех 'HII'-
  resource-блобов всех PE32-файлов (замена `first_resource_string_
  package` на all-вариант). Закрывает minor «found-флаг» (фаза 3).
- Новый внутренний API `collect_string_packages(&Image) ->
  Vec<StringPackageRef>`: file_guid, канал (bare/resource), путь или
  диапазоны, распарсенный пакет. `collect_strings` — плоская проекция
  над ним; RPC `HiiListStrings` без изменений протокола (на HNX99TF
  ~5.7k записей).

### 4.3 insert-at-id в string_pack

`hii/string_pack.rs`:

- `insert_strings_at_ids(body: &mut Vec<u8>, entries: &[(u16, &str)])`:
  SIBT-walk с трекингом текущего id; вставка в разрез SKIP-пропусков —
  `SKIP(n)` переписывается как [новые записи][SKIP(остаток)] с
  корректным классом опкода (SKIP1 ≤0xFF / SKIP2 ≤0xFFFF); id, занятый
  любым блоком (строка/DUPLICATE/…), — ошибка `HiiError::IdOccupied`,
  без тихой замены; пересчёт package length (`update_package_length`).
  Запись — SIBT_STRING_SCSU для ASCII-токенов (формат вендорского
  токен-пакета сверить по пробникам на первом шаге плана; reader
  понимает оба кодирования).
- Resource-канал: обобщение `add_strings_to_resource` → выбор пакета
  по языку внутри блоба + `insert_strings_at_ids` + рост через
  существующие `plan_rsrc_blob_growth`/`write_length_chain`
  (`string_pack.rs:66-107`).

### 4.4 PRC-патч в set_item_visibility

После unsuppress формы (обе ветки `hii/mod.rs:90-123` — bare/RAW и
PE32-resource):

1. IFR-walker расширяется `collect_form_string_ids(body, fid)` — титул
   формы, субтитлы, промпты вопросов, тексты опций внутри формы.
2. В том же package-list (resource-канал) или в string-package секции
   файла (bare-канал) ищется токен-пакет с языком `x-UEFI-AMI`;
   display-пакет — первый STRING-пакет листа с другим языком.
3. Для каждого id из (1): есть непустой текст в display-пакете и нет
   записи в токен-пакете → вставка сгенерированного имени в
   токен-пакет. Пустые в display строки пропускаются (рендерить
   нечего); id с существующей записью не трогаются (опции 2638/2639).
4. Генерация имён: префикс `UPG` + hex-счётчик (`UPG0001`, …),
   уникальность — проверкой по существующим текстам токен-пакета.
5. **Атомарность** по паттерну `precheck_ami_modules`: pre-check
   наличия токен-пакета и выполнимости роста **до** IFR-мутации;
   отказ — `HiiError::PrcPatchUnsupported`, образ не тронут. Нет
   пакета `x-UEFI-AMI` → PRC-патч no-op (не-AMI образы).
6. Write-mode/compression-гейты без изменений; LZMA-обёртка над
   PE32-таргетом рекомпрессируется новым кодировщиком (§4.1).

RPC-маппинг: `IdOccupied`/`PrcPatchUnsupported` →
`failed_precondition` (в духе `hii_error_status`, коммит `22fe28b`).

### 4.5 Миноры

1. **+2/+1 хвостовые байты.** Гипотеза-кандидат: безусловный
   `pad_to(align4(...))` после каждого ребёнка в `build_section`
   (`builder/mod.rs:144-145`) и `build_recompressed_guided`
   (`mod.rs:166-167`) добивает хвост распакованного payload до
   границы 4; +1 байт FFS-хвоста — выравнивание последней секции
   файла. Research-шаг плана подтверждает источник по диффу E7;
   фикс — не паддить после последнего ребёнка (семантика оригинала).
   Безвредно на железе (E7 жив), цель — чистый дифф.
2. **`ops::rebuild` GuidSection-таргеты.** `target_path`
   (`ops.rs:130`) получает GuidSection-arm зеркально DFS-обходу
   `find_item`/`find_item_path` (коммит `7e654b0`).
3. **artifact export CWD.** CLI резолвит выходной путь в абсолютный
   на стороне клиента (относительно CWD клиента) перед RPC; движок
   дополнительно отвергает относительные пути (защита от регресса).

## 5. Обработка ошибок

| Ситуация | Ошибка | RPC-статус |
|---|---|---|
| id занят существующей записью | `HiiError::IdOccupied(u16)` | failed_precondition |
| токен-пакет есть, рост невыполним | `HiiError::PrcPatchUnsupported` | failed_precondition |
| no candidate ≤ budget | не ошибка — минимальный кандидат + раскладка роста | — |
| round-trip кодировщика не сходится | `CompressError::RoundTripFailed` (как сейчас) | internal |

## 6. Тестирование и приёмка

**Синтетика (TDD, по правилам цикла):** заголовок энкодера побайтово
(props/dict/size); свип (влезание с добивкой / минимизация); insert-at-id
(разрез SKIP2→SKIP1, занятый id, пересчёт length, DUPLICATE-блок);
multi-package обход (два файла, bare + resource); PRC-патч на
синтетическом PE с package-list из двух STRING-пакетов (`en-US` +
`x-UEFI-AMI`): появление UPG-записей на точных id, no-op без
токен-пакета, отказ до мутации при негrowable .rsrc.

**Real-image `#[ignore]` на HNX99TF** (продление живых тестов
`real_image.rs`):

- (a) `hii string list` ≈5.7k записей, обе строки-языка HII-файлов
  (en-US и x-UEFI-AMI);
- (b) unhide 901 → токен-пакет содержит записи на 4894/4965/4969
  (id 5071 с пустым текстом — пропущен), display-пакет не изменён;
- (c) рекомпрессия Setup-файла после unhide влезает в исходный слот
  0x161a1 (ожидание ≤0x1611B) — файл не растёт;
- (d) full-flash round-trip и repatch-stability остаются зелёными;
- (e) вне файла ABBCE13D байты образа идентичны оригиналу (slot-fit
  держит раскладку).

**Финальная HW-фаза (прошивает пользователь, движок готовит):**

1. Сборка кандидата чистым движковым путём: `image open` (оригинал,
   Write) → `hii form set-visibility 'abbce13d-…:0x10:0#901' --visible`
   → `image save`.
2. Побайтовая верификация пробниками (`refs/amibcp/probes/fvmap.py`):
  карта FV, дифф декодированных потоков, FIT не задет.
3. Прошивка внешним программатором; чеклист: POST проходит, видео
   есть, Setup → форма «CPU HWPM State Control»: заголовок и подписи
   вопросов/опций непустые, опции переключаются.
4. Результат — аддендум отчёта `docs/reports/`, актуализация TODO.
   Опционально (до начала работ): подтверждение предсказаний §3.2
   отчёта на уже-прошитом E7 — пустой заголовок при видимых значениях
   в скобках.

## 7. Риски и открытые вопросы

- **Каузальность PRC-механизма** — сильная корреляция, но не
  доказательство; закрывается финальной HW-фазой. Если подписи
  останутся пустыми при наличии токенов — возврат к реверсу AMITSE
  (вне этого цикла).
- **Имена токенов** (`UPG…`): неизвестно, влияет ли значение имени на
  рендер AMITSE (токены видимых форм — вендорские `PRC…`). Префикс
  нейтральный, коллизии исключены; при живом отказе — эксперимент с
  вендорским паттерном имён на HW-итерации.
- **API liblzma-биндинга** (lc/lp/pb raw-LZMA1) проверяется первым
  шагом плана; запасной путь — прямой `liblzma-sys`-вызов.
- **SIBT-формат токен-пакета** (SCSU vs UCS2) сверяется по пробникам;
  writer поддержит фактически найденный.

## 8. Влияние на компоненты

- **uefi-engine**: `compress.rs` (энкодер), `builder/mod.rs:162-185`
  (slot-fit, хвосты), `hii/{strings,string_pack,mod,ifr}.rs` (§4.2–4.4),
  `ops.rs` (GuidSection-arm), `rpc/server.rs` (маппинг новых ошибок).
- **uefi-proto**: без изменений протокола.
- **uefi-cli**: резолв абсолютного пути artifact export.
- **TUI/Gateway/WebUI**: не затронуты.
- **Инфраструктура**: `rust-builder.containerfile` (+`xz-devel` или
  static-фича), Cargo.toml workspace.
