# Спека: мини-цикл «page-hijack-op» — in-place захват страницы TSE (E18)

> Дизайн-документ, 2026-09-04. Статус: подход согласован с пользователем
> 2026-09-04 (выбор «A — канальный эксперимент одним образом» после
> скоуп-решения «hijack сначала, genuinely-new страница — следующим
> циклом»). Источник: отчёт ami-patch-op §4
> (`docs/reports/2026-09-03-ami-patch-op.md`), разведка $SPF от
> 2026-09-04 (сессия исследований). Закрывает HW-вопрос «что читает TSE
> для рендера страницы» экспериментом на живом железе.

## 1. Контекст и проблема

E16 (form-add): форма + строки в живом Setup-формсете создают реальную,
но **невидимую** страницу-«стену» — меню TSE строится не из IFR, а из
метаданных AMI (файл AMITSESetupData, контейнер `$SPF`). E17 +
ami-patch-op закрыли механику (правки $SPF/PE32 payload-секций переживают
`build_image`), но семантика регистрации не разобрана: writer пишет
108-байтовые записи неизвестно куда, аппенд в хвост контейнера ничем не
регистрируется. Полное RE контейнера (таблицы, строковый мост, аддитивная
вставка) — большой отдельный цикл с высоким риском неработающего первого
образа.

Решение этого цикла: **не добавлять страницу, а захватить существующую** —
переписать in-place, без изменения длин, IFR формы-жертвы и её записи в
$SPF. Вся адресация контейнера остаётся валидной автоматически (уроки E9
о недопустимости сдвигов соблюдены тривиально: ничего не сдвигается).

Побочный продукт — диагностика каналов рендера (см. §6), которая
определит содержание следующего цикла («новая страница»).

## 2. Данные разведки (HNX99TF, побайтово, 2026-09-04)

### 2.1 Контейнер $SPF

Путь: файл `FE612B72` AMITSESetupData (FV2, @0xa9c708) → GUIDed-LZMA
(слот 0xC2C4, LZMA-alone) → декомпрессат 0x7719C → секция **0x18**
FREEFORM_SUBTYPE_GUID (тело 0x77174 = контейнер) + UI-секция.

Хедер контейнера: `+0x00` GUID файла, `+0x10` сигнатура `"$SPF"`,
`+0x14` u32 0x200, `+0x18` u32 0x210, `+0x24` GUID EC87D643 (varstore
«Setup»), `+0x38` u32 **0x48 = размер записи**, `+0x3c` u32 0x60,
`+0x40` 6 u32-смещений хвостовых регионов (0x7dbc, 0x73f0c, 0x76614,
0x7663c, 0x770cc, 0x77164), `+0x60` малая структура (2,3,4), `+0x70`
главная таблица — 190 возрастающих u32 (0xbc…0x674c, обрыв нулем @0x364).
Семантика таблиц и хвостовых регионов **не разобрана** — и для этого
цикла не нужна.

### 2.2 Записи = 72 байта, глобальный последовательный массив

Всего 389 записей-вопросов (подпись `f8 ff ff ff ff ff ff ff` @+36 +
`01 00 01 00` @+44). Раскладка (побайтово подтверждена на 4G-записи
@0x99E8: qid 0x3B, ifr 0xDD3, счётчик 0x10066):

```
+0    qid u32                    +12   u16 0xFFFF (у всех 389 — НЕ pageId)
+4    u32 (0; изредка 1/2)       +14   u16 0
+8    u16 тип (6/11 — вопросы;   +16   u8 access (0x09 у 4G) + 3 байта
      8 = прочий тип, без подписи)
+10   u16 0x0C                   +20   u32 (UE-референс мэтчит здесь varstore-id)
+24   u32 СЧЁТЧИК — монотонный   +28   u32 ifr-offset (абс. смещение опкода в
      через весь контейнер              form-пакете, правило E9)
      (…0x1005F→0x10060→0x10061…)
+32   u32 0                      +36   f8 ff ff ff ff ff ff ff (подпись)
+44   01 00 01 00                +48   u32 (UE-референс мэтчит здесь qid u16)
+52   u8 failsafe                +53   u8 optimal
+54   нули до 72
```

Записи идут кластерами по формам (у формы 10002 — кластер 0x9880..0x9a78,
7 записей, ifr 0xC8E…0xDFE возрастают внутри кластера и между
кластерами). Ассоциация «запись ↔ форма» — по правилу **ifr-offset ∈
диапазон IFR-тела формы**; это и есть рабочий locator записей жертвы.

### 2.3 Структуры страниц (не трогаем, зафиксировано для истории)

Регион @0x3bc+: `u16 01 00 | u16 form-id | u16 0 | u16 ? | u16
последовательность(1,2,3…) | u32 0 | u32 0x3A (одинаково у всех) | u32
control-count | u32[] список` переменной длины. Списки контролов имеют
стрид 0x40 и **не совпадают** с ifr-offsets записей соответствующих форм —
семантика моста «страница → контролы → рендер» не разобрана. В этом
цикле структуры страниц не редактируются.

### 2.4 Происхождение бага 108-байтового writer'а (закрывает вопрос TODO)

UEFI-Editor (`scripts.ts:112-137`) строит regex по IFR-байтам вопроса и
вычисляет смещения как `(index + 32) / 2`, `(index + 104) / 2`,
`(index + 106) / 2` — это **hex-символы**, делённые на 2 → байты 16, 52,
53. Константы движка (`AMI_PAGE_ID_OFFSET=24`, `AMI_ACCESS_LEVEL_OFFSET=32`,
`AMI_FAILSAFE_OFFSET=104`, `AMI_OPTIMAL_OFFSET=106`, `AMI_RECORD_SIZE=108`)
взяли hex-символьные смещения как байтовые. Правильная раскладка — §2.2.
Замена legacy-writer в formset-add — не-цель (§7).

### 2.5 Открытый строковый мост (не-цель, зафиксировано)

prompt-id 4G-записи = 0x1A3, но в строковом пакете Setup-модуля
«Above 4G Decoding» = id 108 (0x6C). Записи индексируют другую строковую
таблицу (кандидаты: собственный строковый пакет AMITSE/amitseSct, другая
языковая ветка, иная база нумерации). Поэтому string-id записей в этом
цикле НЕ редактируются (§3).

## 3. Решение

Три правки, все — существующей техникой; суммарный рост образа — только
от appended-строк; $SPF и IFR не меняют длину.

1. **Строки** (машина E16, `string_pack::add_strings_to_resource`):
   аппенд `title`, `prompt`, `help` в строковый пакет Setup-модуля.
2. **IFR, in-place, та же длина**: в теле формы-жертвы переписать u16
   string-id'ы: title-id у FORM-опкода, prompt-id/help-id у перечисленных
   вопросов. Смещения опкодов не меняются → ifr-offset'ы записей остаются
   валидными без правки. Реализация — поверх существующего IFR-walker'а
   (gates/hii-парсер знает границы форм и вопросы, правило E9 проверено).
3. **$SPF, in-place, та же длина**: найти payload-секцию $SPF
   (`ami-patch-op`: `find_ami_module` + `find_payload_path` /
   `is_pfs_payload`), просканировать тело на записи-вопросы (сигнатура
   §2.2 — тот же подход, что у UEFI-Editor), отфильтровать по правилу
   «+28 ifr-offset ∈ IFR-диапазон формы-жертвы», у записей перечисленных
   qid записать **только** failsafe@+52 / optimal@+53. Прочие поля записей
   и все структуры контейнера не трогаются. AMITSE PE32 не трогается
   вообще.
4. **Атомарность** (дисциплина c316da9): precheck до первой мутации —
   форма найдена в формсете; каждый перечисленный question_id существует
   в IFR формы; каждому qid соответствует ровно одна запись в $SPF
   (qid + ifr-диапазон, двойной ключ). После precheck — Err-путей нет;
   обе правки помечают Rebuild от пути payload-секции (каскад через
   LZMA-обёртку уже работает).

## 4. API

Новая op `hii form hijack` (proto + RPC + CLI), схема в духе E16:

```json
{
  "selector": {"formset": "899407D7-99FE-43D8-9A21-79EC328CAC21", "form_id": 10007},
  "title": "UEFIPATCHER E18",
  "questions": [
    {"question_id": 23, "prompt": "PATCHER Q", "help": "PATCHER H",
     "failsafe": 1, "optimal": 1}
  ]
}
```

`question_id` — число (u16, как в существующих item-схемах `schema.rs`).
Ответ: appended string-ids, список (qid → запись @offset, старые/новые
fs/opt), подтверждение same-length инвариантов. CLI: `uefi-cli hii form
hijack --image … --file schema.json`. Ошибки: $SPF недоступен →
`AmiFilesNotFound` / `MutationBehindCompression` (переиспользуем);
форма/вопрос/запись не найдены — существующий NotFound-класс `HiiError`
(точный вариант или один новый — фиксируется в плане).

## 5. Приёмка

- **Unit (синтетика)**: фикстуры с живым 72-байтовым форматом (байты из
  §2.2): сканер находит записи по ifr-диапазону; hijack меняет ровно
  fs/opt у ровно перечисленных qid; длины IFR-тела и $SPF-тела не
  изменяются; precheck-отказы (qid без записи / две записи / вопроса нет
  в IFR) не мутируют дерево.
- **Unit (LZMA-слот)**: $SPF за синтетической GUIDed-LZMA-обёрткой —
  после build слот занимает исходный размер (slot-fit), правки видны в
  re-parse, дифф confined к слоту.
- **Real-image (HNX99TF, `#[ignore]`)**: hijack известной формы (для
  теста — любой, не обязательно жертва прошивки) → `build_image` →
  flash-дифф confined ровно к двум слотам (Setup-модуль: строки + IFR;
  AMITSESetupData: fs/opt); файл AMITSE байт-в-байт оригинал; длина
  IFR-тела формы и тела $SPF-секции не изменились; строки находятся в
  re-parse; записи в собранных байтах содержат новые fs/opt.
- **Оракул до прошивки (ручной, AMIBCP)**: пользователь открывает
  собранный образ в AMIBCP — факт «увидел/не увидел» новые дефолты
  вопроса подтверждает, что правка легла туда, откуда читает AMIBCP.
  Гейтом цикла не является.
- **E18 на железе (чеклист пользователя)**: прошить, открыть страницу
  жертвы: (a) заголовок = «UEFIPATCHER E18»? (b) текст вопроса = наш?
  (c) значение по умолчанию (после Load Optimal) = flipped? (d) смена
  значения сохраняется? (e) меню без «стен», соседние страницы целы?

## 6. Диагностическая матрица исходов E18

| Наблюдение | Вывод | Следующий цикл |
|---|---|---|
| Заголовок и тексты = наши | IFR+строки — канал рендера TSE | новая страница = клон структуры страницы + IFR |
| Тексты вопроса наши, заголовок старый | контент из IFR, заголовок из метаданных | точечная правка title-поля структуры страницы |
| Ничего не изменилось | TSE рендерит из собственных таблиц | строковый мост §2.5 + клон страницы с записями |
| Дефолт не flipped (ожидалось) | fs/opt мертвы (линия E13) | дефолты — только StdDefaults (E14) |

Матрица определяет содержание следующего цикла, но не гейт этого:
успех цикла = собранный, верифицированный образ + заполненная строка
матрицы от железа.

## 7. Не-цели (явно за рамками)

- Регистрация **новой** страницы (аддитивная вставка в таблицы $SPF) —
  следующий цикл, по итогам §6.
- Строковый мост записей (§2.5) и правка string-id в записях.
- Структуры страниц (§2.3), главная таблица, хвостовые регионы.
- Правки AMITSE PE32 (form-id списки) — не требуются.
- Замена legacy 108-байтового writer'а в formset-add — остаётся
  задокументированным как мёртвый путь (§2.4) до цикла «новая страница».
- Пересчёт PE-checksum модулей (унаследованное, TODO).

## 8. Риски

- **TSE рендерит из собственных таблиц → видимых изменений нет** —
  главный риск; это осознанный исход-результат (§6, строка 3).
- **fs/opt мертвы** (ожидаемо по линии E13: SDP-колонки AMIBCP на HNX —
  мёртвый дисплей; E14: живые дефолты — StdDefaults NVRAM). Проверяем
  собственной правкой, не выводом AMIBCP.
- **Жертва невидима сама по себе** — исключено выбором пользователя из
  живого меню.
- **Слот LZMA**: $SPF не растёт (та же длина — компрессия может дать
  иной размер потока, slot-fit `compress_lzma_fit` возвращает минимум;
  запас слота 0xC2C4 у AMITSESetupData велик); Setup-модуль растёт
  только на строки (E16 доказал запас слота).
- **Двойной ключ qid+ifr** может не сойтись, если у жертвы вопрос без
  записи (текст-контролы без f8-подписи): precheck потребует запись
  только для перечисленных в схеме qid.
