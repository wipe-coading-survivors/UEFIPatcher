# Предпосылки для рекомпрессии LZMA/GUID_DEFINED в билдере

> Findings-документ (оценка сложности), 2026-08-14. Оценивает пункт TODO
> «Спека: рекомпрессия LZMA/GUID_DEFINED в билдере» (issue IV, вариант
> «Полный (рекомпрессия)»). Выполнен в рамках брейнсторма фазы PE-resource
> HII extraction — по решению принят вариант C: read-only фаза сейчас +
> отдельная спека/фаза рекомпрессии сразу после.
>
> Источники: `crates/uefi-engine/src/{builder/mod.rs, decompress.rs,
> parser/section.rs, types.rs, ffs.rs}`, исходники крейта `lzma-rs` 0.3.0
> (~/.cargo/registry), референс `refs/UEFITool-ai-fork/common/ffsbuilder.cpp`.

## Вердикт

Средняя сложность: ~6 задач, одна SDD-фаза. ~80% механики уже есть в
движке; сложность сконцентрирована в двух точках — компрессор-примитив и
ветка recompress в `build_section`. Закрывает issue IV целиком (все
мутации внутри сжатия, не только HII-видимость).

## Что уже готово (не надо делать)

- **Сериализация детей сжатой секции**: `build_section`
  (`builder/mod.rs:105-131`) уже собирает children-поток с 4-байтовым
  выравниванием — эквивалент первых 80 строк референсной `buildSection`.
- **Пересчёт размеров/чексуммов по цепочке**: `set_section_size`
  (обычный + section2/ExtendedSize, `builder/mod.rs:151-164`),
  `set_ffs_size` (FFSv2 u24 + FFSv3 u64, `:137-149`),
  `recompute_ffs_checksums` (header-checksum + `FFS_ATTRIB_CHECKSUM`,
  `:166-183`).
- **Volume-level reflow**: `build_volume` (`:41-72`) пересобирает файлы,
  паддит до исходной длины тома, честно возвращает `SizeMismatch` при
  переполнении — рост файла после рекомпрессии уже обработан.
- **Метаданные компрессора**: `GuidedSectionParsingData.dictionary_size`
  (`types.rs`) уже вычисляется из оригинального стрима
  (`decompress::lzma_dictionary_size`); оригинальный LZMA-alone-заголовок
  (props-байт lc/lp/pb + dict size) остаётся в `node.body`. Уточнение по
  верификации 2026-08-14 (см. ниже): параметры оригинала переиспользовать
  не нужно — энкодер lzma-rs пишет props 0x5D (совпадает со всеми секциями
  HNX99TF) и dict 8 MB (меньше оригинальных 16 MB — безопасно: стрим без
  дистанций, скрэтч-требования декодера ниже). Совместимость с EDK2
  обеспечивается форматом (known size, без EOS) + round-trip self-check.
- **Guided-заголовок не надо пересобирать заново**: layout нашей ноды —
  `header` = 4/8 байт section-header, `body` = GUID + DataOffset +
  Attributes + payload. Рекомпрессия меняет только payload-хвост body;
  префикс (GUID/DataOffset/Attributes) копируется дословно, DataOffset
  остаётся валидным.
- **Фикстуры для TDD**: `tests/fixtures/lzma_guided_section.bin` +
  `.decompressed.bin` — готовая пара (dirty subtree → recompress →
  re-parse → мутация видна).
- **Nop-трюк unsuppress**: `hii/ifr.rs` подменяет опкод с сохранением
  длины (`[0A 82 12 03 40…]` → `[0A 82 29 02…]`, см. тест в
  `hii/mod.rs:74-81`) — PE32-тело не меняет длины, PE-заголовки
  пересчитывать не нужно.

## Чего не хватает

1. **Компрессор-примитив** `compress.rs`: `compress_lzma(input, dict,
   props) -> Vec<u8>` в формате EDK2 — 13-байтный alone-заголовок
   (props-байт, dict size u32, **известный** uncompressed size u64),
   без EOS-маркера — + обязательный round-trip self-check
   (распаковать своим декодером и сравнить с входом; ровно так делает
   референс `ffsbuilder.cpp:717-727, 902-913`).
2. **Dirty-детект**: `subtree_dirty(node)` — true, если собственный
   action узла или любого потомка ≠ `NoAction`.
3. **Ветка recompress в `build_section`**: для GUIDed-LZMA при dirty →
   сериализовать детей → компресс → приклеить к дословному префиксу
   guided-заголовка → `set_section_size`. При clean → verbatim, как
   сейчас (`builder/mod.rs:109`). Tiano-GUID / standard-COMPRESSION (0x01)
   / unknown-GUID с dirty-subtree → явный `BuilderError` (заодно закрывает
   «Минимум» из TODO — честные ошибки вместо silent verbatim).
4. **Edge-тесты**: clean-tree → байт-в-байт (существующие
   `real_image_full_flash_round_trip` и `real_image_full_flash_
   repatch_stability` обязаны остаться зелёными — рекомпрессия только
   dirty-поддеревьев); dirty → длина образа сохранена, re-parse видит
   мутацию.
5. **Real-image `#[ignore]` тест**: мутация внутри LZMA (HII-кейс фазы 6
   или UI-секция `1/13/2/1` из issue IV) → build → re-parse → мутация
   материализовалась в байтах.
6. **CLI/TUI**: человекочитаемое сообщение об ошибке компрессии/барьера.

## Риски и mitigations

1. **Совместимость с EDK2-декодером прошивки** (главный). Round-trip
   self-check и re-parse валидируют наш декодер, а не железный.
   Mitigation: копировать props+dict из оригинального стрима, точно
   следовать формату BaseTools LzmaCompress (известный size в заголовке,
   без EOS). Окончательное доказательство — только прошивка на железе;
   зафиксировать в спеке как acceptance-риск.
2. **`lzma-rs` 0.3.0 не экспортирует публичного LZMA1-компрессора** —
   УТОЧНЕНО/ОПРОВЕРГНУТО верификацией 2026-08-14: локальная копия крейта
   из registry (та же 0.3.0, что в Cargo.lock) экспортирует публичный
   `lzma_rs::lzma_compress_with_options` (`src/lib.rs:70`, без feature-gate);
   опция `UnpackedSize::WriteToHeader(Some(len))` пишет ровно формат EDK2
   LzmaCompress — известный size в 13-байтном alone-заголовке, без EOS.
   **Решение: вариант A — публичный lzma-rs компрессор** (ноль новых
   зависимостей). `xz2` и internals больше не рассматриваются.

## Верификация 2026-08-14 (probe `hack/recompress_probe.py` + Rust-проба)

- Энкодер literal-only (без LZ-матчей; контроль на случайных байтах —
  ratio 1.014), но реальные firmware-блобы жмёт до 0.346–0.426:
  блоб `1/13` (PE32+UI+VER) 106 858 → 36 997 (0.346); крупнейший блоб
  образа 637 034 → 271 177 (0.426); нули 65 536 → 1 678 (0.026).
  Скорость 2–12 мс на секцию.
- Заголовок вывода: props 0x5D, dict 0x800000, known size — байт-в-байт
  формат EDK2. Round-trip валидирован двумя независимыми декодерами:
  lzma-rs (Rust) и liblzma (python `lzma.FORMAT_ALONE`) — оба дают
  байт-идентичный исход.
- Ёмкость HNX99TF: FV0 free=0, **FV1 free=2 033 KiB**, FV2 free=0.
  Рост секции 1/13 после пересжатия: +11 KB (запас ~180x); худший случай
  «пересжать все LZMA-секции FV1» ≈ +0.85 MB < 2.03 MB. Мутации внутри
  LZMA в FV0/FV2 (нет свободного места) → честный `SizeMismatch` от
  `build_volume` — документируемое ограничение.
3. **Выравнивание файлов при reflow** (вторичный): `build_volume`
   выравнивает только на 8; FFS-файлы с alignment-атрибутом >8 при
   пересборке середины тома могут быть размещены неверно. Сейчас это не
   проявляется (real-image remove-тест пересобирает весь FV align8 и
   проходит); при спеке — проверить `fixed`/`alignment_bytes` поля и
   референсную обработку alignment (`ffsbuilder.cpp`, buildVolume).
