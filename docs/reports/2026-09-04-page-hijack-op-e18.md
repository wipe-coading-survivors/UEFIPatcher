## 1. Артефакт E18

- Кандидат: `refs/amibcp/e18-page-hijack.bin`, 16 МиБ,
  sha256 `d02d5f79b58662512ec9724c10660654221e5072f58904f56eb971ebb3b75c9f`
  (база — оригинал `HNX99TF_200525_original_E5C88C6F.bin`,
  sha256 `7e9d25443d5955e990f5f24cd1e7288d82e6655eb9c0f9f8c1ec5851de6a1c5d`).
- Жертва: форма **10029 «PCI Subsystem Settings»** (Advanced; единственная,
  покрытая real-image гейтом), вопрос **qid 59** (one_of 0/1), запись
  $SPF `rec@0x99E8`, IFR-спан `[0xC80..0xEBA)`.
- Правки: title → string 749 «UEFIPATCHER E18», prompt → 750, help → 751
  (same-length перезапись string-id в IFR); $SPF fs/opt **0/0 → 1/1**;
  3 строки аппенднуты в строковый пакет Setup-модуля.
- Команды (полнота для воспроизведения):

```

  --target 899407d7-99fe-43d8-9a21-79ec328cac21:0x10:0#10029 \
  --file /tmp/e18-schema.json \
```

Побайтовая верификация артефакта (независимо от гейт-теста): 75 271
изменённый байт, все строго внутри слотов Setup `[0x8D1760,0x8D7BF8)` и
$SPF `[0xA99508,0xAA89E4)`; AMITSE и все остальные файлы байт-идентичны;
layout без сдвигов (новый LZMA-поток Setup короче, хвост слота занулён —
slot-fit); re-parse сохранённых байтов отдаёт title «UEFIPATCHER E18».

## 2. Оракул AMIBCP (до прошивки)

- E18: «The ROM file has unsupported string blocks. BIOS strings and
  Setup features not supported» — Setup-дерево отключено, AMIBCP открыл
  файл в деградированном режиме (вкладки без Setup).
- Классификация: **E16 (`e16-form-add.bin`, строковые аппенды, прошитый и
  загружавшийся образ) валится так же** → ошибка — свойство образов с
  аппендом строк, а не регрессия E18. Для образов без строковых правок
  оракул работал (E15, кросс-чек 4G-дефолтов 2026-09-03).
- Вывод для процесса: AMIBCP-оракул неприменим к образам со строковыми
  аппендами; «увидел/не увидел» в этом классе невоспроизводимо. По спеке
  §5 оракул гейтом не является — на решение о прошивке не повлиял.

## 4. Матрица §6 — заполненная строка

| Наблюдение | Вывод | Следующий цикл |
|---|---|---|
| Страница-жертва исчезла из меню целиком; наши тексты нигде не появились; остальные страницы и их строки/хелпы целы; строковые аппенды не сломали рендер глобально | жёстче строки 3 «ничего не изменилось»: TSE строит меню не из IFR-текстов — правка IFR string-id на HII-id вне строкового пространства TSE **убивает страницу** (форма/страница отбрасывается при нерезолве). Заголовки/тексты живут в собственных таблицах TSE за строковым мостом §2.5 (0x1A3 vs 0x6C) + структурах страниц §2.3 | разбор строкового моста (куда указывают 0x1A3: amitseSct / другая ветка / иная база нумерации) и семантики «страница → контролы → рендер» (§2.3, стрид 0x40); только затем — клон страницы с записями, указывающими в мост |

Механизм отбрасывания страницы не однозначен между двумя кандидатами
(различить в следующем цикле): (i) нерезолв title-id 749 через мост →
страница не попадает в меню; (ii) нерезолв любого string-id вопроса
(prompt/help 750/751) → TSE отбрасывает страницу целиком. Оба требуют
одного и того же следующего шага.

## 5. Что E18 доказал попутно (runtime-факты)

- Пересборка движком (build_volume, LZMA lzma-rs, slot-fit с нулевым
  хвостом) **обоих** слотов — Setup-модуль и $SPF — загружается платой:
  меню полноценно, страницы рендерятся, данные читаются. Класс образов
  «recompressed $SPF» hardware-подтверждён (до E18 $SPF пересобирал только
  python-билдер E13).
- Строковые аппенды (3 строки) не ломают загрузку HII-строк TSE: строки и
  хелпы всех остальных страниц на месте.
- Same-length IFR-правки безопасны структурно (форма парсится, соседние
  формы целы) — но семантически string-id обязан резолвиться в
  пространстве TSE, иначе страница теряется.
- `--setupdata-guid FE612B72-…` на HNX обязателен и достаточен: запись
  q59 найдена и изменена с первого раза по полному пути CLI → RPC → engine.

- Мини-цикл page-hijack-op **закрыт**: op `hii form hijack` реализована,

- До того цикла: $SPF fs/opt как канал дефолтов на этой плате закрыт
