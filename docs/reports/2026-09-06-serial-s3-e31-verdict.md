# Отчёт: S3 — вердикт E31 (закрытие ступени)

> 2026-09-06, ветка `serial-console`. Прошит кандидат
> `~/E31/E31-candidate-d30cca1c.bin` (sha256 `d30cca1c…`, отчёт
> `docs/reports/2026-09-06-serial-s3-e31-pack.md`). Гейт S3: (a) пункты
> видимы, (b) смена baud меняет скорость COM. Ниже — наблюдения
> владельца дословно, разбор симптомов и офлайн-проверки, закрывшие
> вопрос без повторного прошива.

## 1. Наблюдения владельца (досрочно, дословно)

Первая сессия (после прошивки E31):

> не сохраняет выбор типа терминала через F10 (шоткат на сохранить и
> выйти) или явного выбора "сохранить", более того если изменить другие
> параметры и нажать F10, то идет записть и хост перегружается, в случае
> изменения настройки терминала - просто выходит на загрузку ОС, то есть
> нет события о том, что были внесены изменения. далее если попробоват
> изменить baud-rate можно выбрать что угодно, но останется 115200,
> попробовал изменить параметры ком-порта (2f8, irq3) сразу ощутил
> заторможенность интерфейса (в серийном порту, даже не сохраняя),
> сохранил -> перезагрузился, вывод на серийны порт остался 'Version
> 2.18.1263 …', но если нажать вход в настройки биоса, но только эти
> надписи - ничего более, можно в обычном терминала (видеокарта+
> клавиатура непосредственно подлкюченные) нажать вход в настройки
> биуса отерывается основной экран и TUI зависает. сбрасил кмос
> джампером - помогло - вернулись к изначальной ситуации

Поправка (той же датой, после перепроверки):

> поправка: бауд-рейт можно изменить и тип терминала (но через
> видеокарту + клавиатуру и это запоминается и смен значений
> происходит - в серийный порт начинает валится мусор), повторно
> проверяю через серийную консоль - подтвердаю - сохраняется, не имеет
> значеняи тотько тип терминала UTF-8/ФЫСШШ

Скриншот Setup (страница «Serial Port 1 Configuration»): пункты
**Baud Rate [115200]** и **Terminal Type [VT-UTF8]** на месте, popup
терминального типа открывается с четырьмя нашими опциями
(VT-UTF8/VT-100+/VT-100/ANSI), help-панель справа показывает наш хелп
«Serial console terminal type (applies on next boot)».

## 2. Вердикт

- **(a) Видимость — ПОДТВЕРЖДЕНА.** Оба пункта рендерятся: строки
  (prompt + help-панель), опции, дефолты (115200/VT-UTF8), popup
  интерактивен. Полный канал S3 (IFR-сплайс → строки → $SPF-запись →
  клон страницы) работает на живом TSE.
- **(b) Baud → скорость COM — ПОДТВЕРЖДЕНА** (поправка владельца):
  смена значения через локальную консоль сохраняется и действует —
  «в серийный порт начинает валится мусор» = UART перепрограммирован
  glue на новую скорость, смотрящий терминал остался на старой.
  Цепочка вопрос → NVRAM `Setup[0x5D]` → glue → SetAttributes →
  железо доказана end-to-end. Правка через серийную консоль по
  перепроверке владельца тоже сохраняется.
- **Terminal Type — сохраняется и применяется, видимых отличий нет.**
  glue выбирает GUID терминального чайлда по `Setup[0x5E]`
  (`kTerminalGuidMap`, VT-UTF8/VT-100+/VT-100/PC-ANSI), т.е. значение
  функционально доходит до TerminalDxe; ASCII-вывод загрузки между
  режимами не различается — «не имеет значения» = отсутствие видимой
  разницы, не отказ.

**S3 ЗАКРЫТА: гейт пройден.**

## 3. Разбор симптомов первой сессии

1. **F10 на наших вопросах — выход без перезагрузки, на нативных —
   запись + перезагрузка; baud в первой сессии показался
   «неизменяемым».** Факт различия F10-поведения — наблюдение владельца
   (дословно, §1); функциональной ошибки нет — поправка владельца
   подтвердила: значения сохраняются (в т.ч. по перепроверке через
   серийную консоль). **Механизм — НЕПОНЯТОЕ ПОВЕДЕНИЕ (отложено):**
   гипотеза RESET_REQUIRED-флагов (`0x00` у наших опкодов vs
   `0x10/0x10` у нативных, см. §4) владельцем оценена как сомнительная
   (2026-09-06) и принята как отложенный вопрос, не как диагноз.
   Дешёвая мера UX-паритета (зеркалировать `0x10/0x10` в билдере при
   следующей прошивке чего-либо) остаётся в парковке — независимо от
   механизма.
2. **COM-переезд (2F8/IRQ3) → тормоза серийного UI ещё до сохранения,
   после сохранения — серийная консоль глухая (только баннер),
   локальная открывает Setup и TUI виснет, лечение — сброс CMOS.**
   Факт воспроизводим и изолирован (S2-масштаб, не S3). **Механизм —
   НЕПОНЯТОЕ ПОВЕДЕНИЕ (отложено):** цепочка «SerialDxe фикс 0x3F8 →
   записи в пустоту с таймаутами → синхронный ConSplitter-дрен» —
   гипотеза, владельцем оценена как неправдоподобная («фантастика»,
   2026-09-06); принята как отложенный вопрос, не как диагноз.
   Кандидаты на лечение (S4: resource-aware serial / донорский AMI
   SerialIo; либо guard в glue) сохраняют смысл как способ сделать
   стек устойчивым к переезду — независимо от точного механизма клина.
3. **«Только надписи при входе в настройки через серийный порт» после
   COM-переезда** — часть симптомокомплекса п.2 (консоль не поднялась
   на переехавший UART; баннер печатается более ранним звеном).

Итерация S3 не требуется: гейт (a)+(b) закрыт поправкой владельца;
поведения (1)/(2) зафиксированы как непонятные и отложены (зеркало в
TODO.md).

## 4. Офлайн-проверки после вердикта (выбрасываемый проб)

Проба по оригиналу E5C88C6F и кандидату d30cca1c (одноразовый
`tests/e31_probe.rs`, удалён; метод — движковые API: скан записей,
`spf_record_resolves`, строковые таблицы, классификация записей
контейнерa). Факты (для будущих циклов):

- **Флаги вопросов**: все 30 нативных one_of Setup-формсета несут
  `qflags=0x10, oflags=0x10` (RESET_REQUIRED + байт one_of); единый
  нативный вопрос с `0x00/0x00` — q21 (numeric, access=1) — и наши
  0-флаги реально коммитились и сохранялись на железе → **флаги не
  гейтят коммит**, дело только в UX перезагрузки.
- **Запись $SPF не содержит полей биндинга** (varstore/var_offset
  живут только в IFR-опкоде по `record.ifr`); раскладка 72Б:
  qid u32@+0, +4 флаги-класса (0/1), type u16@+8, **u16@+0xA = seq
  страницы**, u16@+0xC = 0xFFFF, access u32@+0x10 (9 = обычный,
  1 = класс q21), help u32@+0x14, counter u32@+0x18, ifr u32@+0x1C,
  0 u32@+0x20, сигнатура `f8 ff×7`@+0x24, `01 00 01 00`@+0x2C,
  prompt u32@+0x30, fs/opt@+0x34/0x35, хвост.
- **Шаблон наших записей — q35** (первая запись IFR-спана формы 10019;
  diffs=0 вне перезаписанных полей). При этом q35 сам работает в
  **varstore 21** (SIO-семья), наши вопросы — в varstore 1 «Setup» —
  смешение varstore внутри одной страницы TSE приемлет.
- **Конвенции списков страниц**: 19 страниц — прямые указатели на
  записи, 3 — массивы-группы `{ptr[], метаданные {05 00, str-id, seq}}`,
  смешанных нет; страница 10019 — массивная. Наши прямые записи в ней
  и рендерились, и коммитились → TSE толерантен к прямой конвенции
  даже в массивной странице (детект по записи, не по конвенции
  страницы). Прямой формат можно считать рабочим для будущих вставок.
- **Varstore «Setup»** (EC87D643): декларация в формсете — размер
  0x72 = 114 Б; нативный экстент использования 0..92; наши 0x5D/0x5E —
  в границах декларации и функциональны на железе.
- Заводская длина NVRAM-переменной «Setup» в сжатом NVAR-сторе образа
  не извлечена тривиально (стор в LZMA-секции вне дерева движка);
  вопрос снят железом — значения за офсетом 92 сохраняются и живут
  через перезагрузки.

## 5. Статус лестницы и парковки

- **S0–S3 закрыты.** S5 (redirect) фактически продемонстрирован
  E30+E31: redirect следует настроенному baud. Следующая содержательная
  ступень — **S4** (AMI-стек / resource-aware serial; сюда же лёг
  COM-переезд из §3.2) — по решению владельца.
- Парковки (зеркало в TODO.md):
  1. зеркалировать `0x10/0x10` в `IfrBuilder::emit_one_of` (UX-паритет
     с нативными; механизм F10-различия отложен как непонятый) — при
     любой следующей прошивке;
  2. COM-переезд-клин — непонятое поведение (механизм-гипотеза не
     принята владельцем); лечение — устойчивость к переезду в S4
     (resource-aware serial / донорский AMI SerialIo) или guard в glue;
  3. (опционально) видимая проверка term: рамки TUI в VT-100 vs
     VT-UTF8 — косметика, по желанию владельца.
