# RD450x: PCIe-бифуркация и серийный дебаг — итоговая сага (2026-09-13..14)

Владелец: Lenovo ThinkSystem RD450x (ODM-плата супер-микровского
семейства, Xeon E5 v3 / Grantley, AMI Aptio). Цель: бифуркация
Port 2 → 2×x4 под пассивный рейзер с двумя NVMe + живой серийный
дебаг (RC-трассировка бута CPU/памяти) через TMM SOL.

## 1. Исход

- **Бифуркация решена** на HNX-билде посевом (дважды железом:
  v2, v7 — Port 2 = 2A/2B, обе Optane в ОС) и на супер-микро
  билде (фабрично + **живое UI-переключение**, подтверждено
  владельцем на v8).
- **«Всё сразу на родном билде»** (SOL-дебаг + бифуркация):
  посев-путь на нативе исчерпан и закрыт экспериментом v9
  (2026-09-14: сид доставлен в стор через F9, дисплей
  подтверждает — порт x16, см. §4); направление владельца:
  свои PEI/DXE-модули / патч нативного IIO-полиси (см. §7).

## 2. Механизм (главное открытие)

Единственный живой источник boot-настроек RC на этом семействе —
**посев из NVAR-шаблона**:

- два носителя: RAW-файл `CEF5B9A3` (FV0) + LZMA-копия (файл
  `9221315B`, DXE-том); править согласованно обе (движок
  `hii question set-value` делает это сам);
- доставка сида в рантайм-стор двумя путями: **F9/Load
  Defaults** — копия StdDefaults-шаблона в стор (доказано v9:
  наш сид отобразился как IOU0=[x4x4x4x4]) и **ресид NVRAM**
  при невалидном сторе (PEI `NVRAMPei 34cf8d83…` — мост;
  случился на v2/v7, чьи HNX-базы ехали с пустым регионом);
- **стор путешествует с образом**: TMM-флэшер льёт весь 16MB
  включая NVRAM-регион — v5/v9 поднялись с фабричного стора
  из образа (ресида на валидном сторе нет), v6 «выжил» не сам,
  его везла база ds1 (сейвы владельца внутри образа);
  «зеркала настроек в BMC» нет: Supermicro-билд с TMM не
  разговаривал, копиться значениям было неоткуда;
- AMIBCP-правки SDP/IFR инертны для посева (E13); флип байта в
  шаблоне применяется (E14/E15).

Побочный вывод: смена режимов = правка шаблона в образе, либо UI
на билдах с живой проводкой (супер-микро).

## 3. Карта билдов (refs/fw + refs/fw/overclokers/)

| Билд | Бифуркация | Серийка | Прим. |
|---|---|---|---|
| натив-Lenovo (450x-семейство, 8+ копий, один шаблон `bif[04 03 ff ff 04…]`) | ✗ посев НЕ применяется: политика игнорирует ручку (v9: после F9 сид в сторе и на дисплее — порт x16; консольные ручки того же стора применяются) | ✓ Setup-зеркало + RC-дебаг через **BMC/SOL-мост** (Serial Mux/ServerSetup; настройки TMM переживают прошивки) | мир владельца |
| HNX99TF | ✓ посев `0x531–0x534=00×4` (v2, v7) | ✗ код вывода вырезан: ручки Redirection/Debug/Trace в IFR есть, посев Maximum — тишина | «тихий» гиперскейлер; полный образ тянет чужой ME-регион |
| 超微450 ≡ rd450-bf (комьюнити-решение) | ✓ + **UI-переключение работает** (владелец: x16↔x4x4x4x4, три флешки) | ✗ чужой BMC (не Nuvoton), SOL-моста нет; шаблон CR/dbg/trace весь в 00 | v8 = +3 байта посева, физпорт молчит |
| X10DRH1_816 | референс другой платы | — | не шить на RD450x |

Замечание: наблюдение владельца на v8 («дефолт x16») указывает,
что сырой оффсет-рид зоны 0x531 у 超微450 (стор 0x1677, сдвинутая
раскладка против 0x1670) мог быть неточен; UI-цепочка там живая
в любом случае.

## 4. Железные вердикты

- **v2** (HNX+REF3+байт 0x531): первый PASS — Port 2 раздвоен.
- **v6** (ds1+4 байта): ресиды не случилось (рантайм-стор выжил),
  порт x16 при живом рантайм-значении → натив игнорирует ручку.
- **v7** (HNX+полный серийный посев): бифуркация PASS; серийка
  мертва → в HNX нет кода вывода.
- **v8** (超微450+CR/Debug/Trace): бифуркация ✓ (UI тоже);
  серийка/SOL ✗ (микроконтроллер другого вендора).
- **v5** (натив+REF3+биф+консольные сиды Debug=Maximum/
  Trace=Enabled/Redirection=On): первый бут норм — фабричный
  стор из образа; F9 → наш сид + максимальный дебаг → **POST-
  потоп в цикле** (регистры 0x8FFA4xA8), сетап недоступен,
  спас только рефлэш (~30 минут ожидания). Урок: консольные
  сиды — только фабричные значения; Maximum Debug Level на
  этой плате = вечный трейс-цикл (подтвердил память владельца
  о старом ds1-опыте).
- **v9** (натив+REF3+биф, консоль фабричная; побайтно ≡ v4,
  `450x-native-v9-bif-seed.bin`): F9 → F10 → бут дошёл;
  IOU0=[x4x4x4x4] в сторе и на дисплее, Port 2A «Linked as x2,
  Max Width x16», lspci — один 02.0 без 2A/2B. **Вердикт:
  натив игнорирует IIO-ручку окончательно** — тот же стор,
  тот же путь доставки: консоль/дебаг применяются, бифуркация
  нет. Селективность консьюмеров, а не доставки.

## 5. Форензика-цепочка

- «Легенда о PEI-гарде Lenovo» (гугль-AI) **опровергнута по
  механике, подтверждена по сути** (вердикт владельца 2026-09-14):
  потребители есть — 9 PEI-модулей RC читают IntelSetup
  (UncoreInitPeim `a48b1cd7…`, NVRAMPei, PlatformInfo,
  PlatformEarlyInit, OcInit и др.); нативный билд просто не
  консультирует IIO-ручку (захардкоженная политика). Контраст
  на v9: ядра/HT и SOL-дебаг из того же стора тем же F9
  применяются — слотовые ручки не читаются выборочно-намеренно;
  гварда-модуля нет. Отличить «намеренно» от «не проложено»
  должен дизасм R1 (код читает и отбрасывает 0x531 — либо
  чтения нет вовсе).
- **Контрольная матрица ручек натива** (2026-09-14, UI-пробы
  владельца, без прошивок). Живые: ядра/HT; частота памяти
  1600→1866; SOL-дебаг; Link Speed cap (Gen1 на Port 2A);
  PCI-E Port Auto→Disable. Мёртвые: Override Max Link Width;
  бифуркация IOU0/IOU1/IOU2. Ключ: **Port 1 физически сплит
  x4x4 с завода** (I350 на 1A линкуется Gen2 x4, 1B пуст) при
  сторе IOU2=[x8] — политика ширины идёт от таблицы платы,
  ручка не подключена; машина бифуркации на нативе работает.
  Следствие: R1 ищет таблицу; возможен чистый data-патч Port 2
  (x16→x4x4) без единого чужого модуля.
- «AMIBCP правит — не применяется» (2026-09-03) закрыто: AMIBCP
  трогает SDP/IFR (инертно), стор оставался фабричным; ds1
  владельца — тот самый AMIBCP-мод многолетней давности.
- qid-карты **двухвийные**: натив `0x242/0x243/0x244…` vs HNX
  `0x247/0x248/0x249…`; офсеты `0x531/0x535/0x539+x` идентичны.
  Спека §6 исправлена (коммиты `19339ab`, `1da7916`).
- RE-артефакты: `IIO-pei32.bin` (798880, PE32, строки «Invalid
  IOUx Bifurcation»/«busUncore»/«busIio» — валидатор бифуркации,
  розеттский камень для дизасма), `rd450xSPF.bin` (x64 PE,
  $SPF-носитель), `dxe-platform.ffs` (= FFS ABBCE13D,
  IntelRCSetup-драйвер).

## 7. Следующий цикл: свои PEI/DXE вместо чужих билдов

Цель: бифуркация + SOL-дебаг **на родном билде**. По возрастанию
сложности:

1. **Дизасм + патч нативного UncoreInitPeim** — найти
   захардкоженную IIO-политику (розетта: строки валидатора из
   `IIO-pei32.bin`), направить на чтение IntelSetup. Точечно,
   сохраняет весь мир владельца.
2. **Кросс-свап UncoreInitPeim** из ручко-живого билда (HNX) в
   нативный PEI-FV — один RC-семьи; риск HOB-несовместимостей
   версий.
3. **EDK2-интерпозер** (идея владельца) — PEIM между NVRAMPei и
   Uncore: сам по себе бесполезен, пока Uncore не читает ручку
   (натив игнорирует), — становится нужным в паре с (1).
4. DXE-консоль для серийки не нужен: SOL у натива уже есть.

Остаточный дешёвый тест перед циклом (опционально): форс-ресид
при живом образе — v10 с затёртым NVRAM-регионом в образе или
сброс NVRAM средствами TMM. Вероятность успеха низкая
(селективность консьюмеров уже доказана на v9), но это
единственная непроверенная ветка механики посева.

Движку для цикла нужна новая capability: **замена/добавление FFS
в PEI-FV** (механика — как add-FFS, плюс rebuild PEI-тома).
