# Вердикт: NP-E раунд 1 — E36/E37 (v3-цепочка): вис на входе в Setup

> 2026-09-09, ветка `setup-new-page`. Прошивка E36 (`df9c38f0…`) и
> E37 (`0c4d536e…`) — владелец. Оба кандидата из pack-отчёта
> `2026-09-07-setup-np-e36-e37-pack.md`.

Наблюдения владельца дословно:

- **E36** — виснет при входе в BIOS (TUI). Serial:

```
Version 2.18.1263. Copyright (C) 2019 American Megatrends, Inc.
BIOS Date: 10/28/2019 20:28:47 Ver: GHX99014
Press <DEL> to enter setup.Press <F11> to enter boot menu.
Entering Setup...ERROR: Class:3000000; Subclass:50000; Operation: D
```

- **E37** — та же картина (тот же вывод, то же место).

## 1. Сигнатура

`ERROR: Class:3000000; Subclass:50000; Operation: D` —
**байт-в-байт сигнатура E34** (SOFTWARE/DXE_BS_DRIVER, op 0x0D;
вердикт E34, docs/reports/2026-09-07-serial-s4b-e34-verdict.md:13).
Отличие: в E34 строка печаталась **дважды** (два COM-инстанса),
здесь — **один раз**. Пост прошёл (баннер, DEL-приглашение), краш —
точно на входе TSE («Entering Setup...»), до какого-либо рендера.

## 2. Разбор: что общего у E36/E37 с E33/E34 и что от них отличается

E33/E34-класс краша (вердикт E34 §1): при входе в Setup TSE/ConSplitter
LIVE трогает SimpleTextOut/SimpleTextIn-устройства за пределами
ConOut-списка — первый вызов «лишнего» terminal-чайлда роняет машину.
E34 приписал это TermSrc-чайлду; механика класса — любой
terminal-чайлд вне ожидаемого набора.

**Корневая находка ревизии сборки:** кандидаты E36/E37 были собраны
гейтом np на **E35-цепочке (glue v3, 1EF3A7C2)**, а не на планной
**E32-цепочке (glue v2)**. План (§«Схема данных») требует «тройку s4
(SerialIo-донор, TerminalDxe, glue v2)»; гейт Task 5 переиспользовал
хелперы гейта s4c (это E35-флоу) — вместе с ними приехал v3.
Отклонение зафиксировано финальным ревью как «wording nit» —
недооценено: **glue v3 никогда не прошивался** (E35 собран, но не
шился — не понадобился после чистого E34), тогда как v2 доказан
железом (E30–E32, включая вход и рендер Setup на COM).

Отличие v3 от v2 — search-all по **четырём** терминальным GUID
(PcAnsi/VT100/VT100+/VT-UTF8; аддендум S4a §11 — v3 создавался для
сосуществования с TermSrc). Правдоподобный механизм краша: v3
цепляет/создаёт несколько TerminalDxe-чайлдов на serial-порту —
при входе в Setup TSE трогает их (вне ConOut либо через
ConSplitter-мультирежим) → воспроизводится E34-класс. Одна ERROR-строка
(против двух у E34) согласуется с одним падающим инстансом.

## 3. Гипотезы

| # | Гипотеза | Оценка | Дискриминатор |
|---|----------|--------|---------------|
| H1 | glue v3 — E34-класс токсичности terminal-чайлдов | **первичная** | флеш E35 (чистая v3-цепочка, без Setup-правок) — вис ⇒ доказано; либо бут E36v2/E37v2 — бут ⇒ доказано контрфактом |
| H2 | Setup-правки (pageless-REF E36; пустая страница E37; форма; q600/601) валят TSE на построении дерева | вторичная, замаскирована H1 | E36v2/E37v2: если и они виснут — H2 (или H3/H4) |
| H3 | varstore 2 (новая декларация IFR_VARSTORE_EFI) ломает вход TSE | низкая-средняя | бисект: форма без varstore2/вопросов |
| H4 | сдвиг FV1 (Δ=96, 187 файлов) | низкая — бут дошёл до Setup, FFS-обход сместился корректно | бисект при необходимости |

Сток-контекст для H2: goto-REF на форму без страницы (E36) нарушает
сток-инвариант 0/89 — риск был известен (ожидание по E36 — исход (b)
«стена»), но не «вис на входе». E37 регистрирует страницу по
эталонному рецепту (слот 188, B=8, cnt=0 — прецеденты 10009/10003).
Одинаковый симптом E36/E37 говорит против REF/страницы как причины
(они — главное отличие кандидатов между собой).

## 4. Решения (исполнено)

1. Гейт np переведён на планную v2-цепочку (`SerialConsoleGlue.ffs`;
   NP_SERIAL_FILES, real_image.rs) — гейты np1/np2 зелёные на v2,
   полная `--ignored`-серия не регрессировала.
2. Кандидаты пересобраны живым движком (флоу идентичен гейту):
   **E36v2** `~/E36/E36v2-candidate-b1e38008.bin` (sha256
   `b1e3800858e6ecfe58dc64d179b48a9bcc8896458ea6e39ea4b70a8602cbb302`)
   и **E37v2** `~/E37/E37v2-candidate-8e1b476c.bin` (sha256
   `8e1b476cc9644ad74eb391bd85f4d101c1164fb28688d7c0e74cade843aa1f26`).
   Валидация: fv_audit FV1 216→219 (used 0x2efa28 / free_tail
   0x1e05d8), зонный дифф — вне FV1 0 байт, порядок/GUID/тела стока
   сохранены, Δ=96 константный, тройка над 0xFF-хвостом; re-parse
   живым движком ок. Раскладка идентична v3-кандидатам (glue той же
   длины 41 072 Б); семантика страниц/REF — из гейтов np1/np2.
3. E35 (`~/E35/E35-candidate-031df12f.bin`) остаётся
   **форензик-дискриминатором H1**: чистая v3-цепочка без Setup-правок
   и без сдвига. Необязателен, если прошивается E36v2/E37v2 напрямую.

## 7. Раунд 2 (E36v2/E37v2, тем же днём): H1 отвергнута — найден корень

Наблюдения владельца дословно:

- **E36v2** — виснет; serial:

```
Press <DEL> to enter setup.Press <F11> to enter boot menu.
Entering Setup...SC-S1 glue: serial console attached (ConOut updated)
ERROR: Class:3000000; Subclass:50000; Operation: D
```

- **E37v2** — виснет; serial:

```
Press <DEL> to enter setup.Press <F11> to enter boot menu.
Entering Setup...ERROR: ATA device failure
ERROR: Class:3000000; Subclass:50000; Operation: D
```

### 7.1 Чтение вердикта

- **v2-цепочка тоже виснет** → H1 (glue v3) отвергнута как причина:
  вина в Setup-правках или сдвиге (H2/H3/H4), общих для всех четырёх
  кандидатов.
- **Маркер SC-S1 виден впервые за дугу** (E30–E32 его не видели:
  гипотезы — ClearScreen Setup-рендера/stale TextOut). Видимость
  согласуется с крашем ДО первого ClearScreen — т.е. падение в
  инициализации TSE, раньше рендера. Позиция маркера (после
  «Entering Setup...») — отложенная печать/флаш glue-строки, не
  порядок загрузки.
- «ERROR: ATA device failure» (только E37v2) — не коррелирует с
  диффом кандидатов (Setup-модуль/SetupData; ATA-стек не тронут) —
  шум бут-фазы, паркуется.

### 7.2 Корень: дубликат varstore id 2 (статически доказано)

Probe-метод (движковый `check_question_add` на чистом LIVE, ошибки
check — без мутаций) вскрыл инвентарь varstore сток-формсета
(пакет, в который пишет form add): **ids 1..20 заняты**, включая

| id | size | note |
|----|------|------|
| 1 | 0x72 | «Setup» — полон (S3-числа) |
| 2 | 0x2 | **наш «новый» id — а он стоковый**, вопрос q0x7 @0x0 |
| 6 | 0x51, 10 | 0x11c — крупные стоки |
| 20 | 0x9 | последняя занятая проверка |
| 31+ | — | **свободны** («not declared») |

Фикстура np_form.json объявляла varstore **id 2** (0x10, UefiPatcherSetup)
→ все четыре кандидата несли формсет с **двумя декларациями id 2**
(сток 0x2 Б + наша 0x10 Б), а q600/601 писали поверх сток-вопроса
q0x7 @0x0. AMITSE на входе строит storage-карту по декларациям —
дубликат ID = падение до рендера (совпадает с выживанием SC-S1 и
одинаковостью симптома у всех четырёх кандидатов, включая E37 с
зарегистрированной страницей). E16 не вис: его форма не объявляла
новый varstore.

Первопричина ошибки данных: NP-P §10-поправка выбрала id 2 без
проверки занятости (предыдущий скан разведки анкерился не в тот
forms-пакет и показал пустую таблицу — теперь инвентарь снят самим
движком). H4 (сдвиг FV1) и H2 (REF/страница) остаются замаскированными,
но у H3' (дубликат) приоритет — единственное найденное фактическое
расхождение со стоком.

### 7.3 Раунд 3 (исполнено)

Демо-varstore перенесён на свободный **id 31** (граница занятости
проверена; ids 21–30 не проверялись — TODO): np_form.json
(id/var_store_id 31), smoke-вопрос гейта — vs 31 @0x2; введён
`NP_NEW_VARSTORE_ID`. Гейты np1/np2 зелёные (36/36 ignored), 490
unit, clippy/fmt чисты. Кандидаты пересобраны (флоу прежний,
отличие только id varstore): **E36v3** `08f9b3df…`
(`~/E36/E36v3-candidate-08f9b3df.bin`), **E37v3** `d5b60d7d…`
(`~/E37/E37v3-candidate-d5b60d7d.bin`). Валидация: вне FV1 0 байт;
сток порядок/GUID/тела сохранены; сдвиг константный (E36v3 Δ=104,
E37v3 Δ=96 — LZMA-пересжатие даёт разные роста при равной
семантике; инвариант «один Δ на кандидат» держится); fv_audit
216→219; re-parse живым движком ок.

Прошивка — E37v3 в первую очередь (pack §8). Откат прежний
(E32 / E5C88C6F).

## 8. Раунд 3 (E36v3/E37v3, тем же днём): краш сместился — после ClearScreen

Наблюдения владельца дословно:

- **E36v3**, вход по DEL:
  - VGA: «думает» некоторое время, успевает напечатать Error ATA…,
    затем стирает всё с экрана и рисует мигающий курсор на третьей
    строке;
  - serial: стирается, курсор в 1 строку/1 позицию; полный лог:

```
Press <DEL> to enter setup.Press <F11> to enter boot menu.
Entering Setup...ERROR: ATA device failure
ERROR: Class:3000000; Subclass:50000; Operation: D
```

  («не могу подтвердить, но в один момент увидел что-то связанное
  с SC-S1 glue»);
- **E37v3**: виснет при входе как E36v3, стирает и VGA и serial,
  ошибки не видно.

### 8.1 Чтение вердикта

- **Прогресс относительно раундов 1–2**: экран СТИРАЕТСЯ и ставится
  курсор — ClearScreen выполнен → TSE прошёл инициализацию хранилищ
  (дубль varstore id 2 был там и чинился) и падает теперь при
  первом рендере / обходе дерева страниц. Раунды 1–2 висили ДО
  очистки (маркер SC-S1 выживал).
- «ERROR: ATA device failure» мигрирует между кандидатами независимо
  от состава диффа (был у E37v2, есть у E36v3, нет у E37v3) —
  бут-шум, паркуется окончательно.
- E36v3 и E37v3 висят одинаково → страница (разница кандидатов)
  по-прежнему не является самостоятельной причиной.

### 8.2 Сужение подозреваемых (по железным прецедентам дуги)

| элемент v3 | статус |
|---|---|
| форма+строки (E16-класс), REF-инъекция как класс (E18), вопросы на сток-варсторе (E31/E32), цепочка v2+Вопросы S3 (E32) | прошиты и живы |
| **A: новый varstore id 31 + вопросы на нём** (NVRAM-переменная не существует никогда) | **непроверено железом** |
| **B: сдвиг FV1** (E16/E18 slot-fit — никогда не прошивался) | **непроверено железом** |
| C: REF на новую форму (E36v3 — без страницы; E37v3 — с новой пустой) | E18 шил REF только в существующую страницу — новая форма как цель не прошивалась |
| D: форма с вопросами+varstore как таковая | пересекается с A |

## 9. Раунд 4 + КОНТРОЛЬ E32 (владелец): виноват хост, не диффы

Наблюдения владельца дословно:

1. **E37v4** — виснет при входе, стирает экран;
2. **E36v4** — так же;
3. **E32** (рабочий образ дуги, вердикт 2026-09-06: Setup на COM,
   навигация, сохранение) — **так же виснет, стирая экран**;
   «или я что-то путаю и он не должен загружаться?»

Проверено контролем: sha256 `~/E32/E32-candidate-8def2850.bin` =
`8def285059d29acbfbabe4c83709bc8bace496e380d8252e9f27fa00568f82cc` —
байт-в-байт совпадает с pack-хешем E32. Файл цел.

### 9.1 Главный факт лестницы NP-E

**Одни и те же биты (E32) рендерили Setup 2026-09-06 и валят его
2026-09-09.** Значит, текущий блокер — не диффы кандидатов
(varstore/REF/страница/сдвиг/цепочка), а изменившееся состояние хоста
или железа. Контрольный эксперимент, которого не хватало ещё S4b,
проведён владельцем только что.

Согласованность с раундами 1–3: раунды 1–2 висили ДО ClearScreen
(наш дубль varstore id 2 — реальный и починенный); v3/v4 висят
ПОСЛЕ ClearScreen — ровно там же, где сегодня висит и E32. Т.е.
минимум один хост-фактор активен с ~2026-09-08 и маскирует все
последующие диффы; наши v3/v4 могут быть полностью рабочими.

### 9.2 Хост-факторы-кандидаты

| фактор | за | против | проверка |
|---|---|---|---|
| **NVRAM (NVAR-стор @0x800000)** — накопленный мусор эры E33+ (Con*-записи TermSrc/glue-чайлдов), если флешер НЕ переписывает этот регион | hung-буты E33/E34 успевали дописать UEFI-переменные до виса | образ несёт населённый стор-дефолтов; если инструмент пишет весь BIOS-регион — бейзлайн сбрасывается каждой прошивкой | холодный сброс + (план C) образ с битым checksum стора |
| **CMOS RTC** | AMI дублирует Setup в CMOS; с 09-07 CMOS живёт в пост-E34 состоянии | CMOS-clear в протоколе E34 не помог тогда | PSU-off + батарея/джампер на ~5 минут |
| **Железо/ATA** («ERROR: ATA device failure» в бутах 09-09: E37v2, E36v3; в эпоху успеха E30–E32 не упоминался) | мигрирует между кандидатами независимо от диффов; «думает какое-то время» = таймауты | не подтверждено | отключить SATA-диски, повторить вход |

### 9.3 Протокол восстановления (без новых прошивок; на хосте сейчас E32)

1. **Холодный сброс**: PSU-off, CMOS-батарея out (или джампер CLRTC)
   ≥5 минут, собрать, включить → DEL в Setup (образ E32, уже прошит).
   - Setup входит → хост-фактор был CMOS/NVRAM → сразу прошить
     **E37v4** (`~/E37/E37v4-candidate-e097a186.bin`, sha
     `e097a186…`) и провести приёмку pack §3 — дуга NP-E может
     закрыться этим же бутом;
2. Если E32 после холодного сброса всё ещё висит → **отключить
   SATA-диски** (ATA-фактор) → DEL:
   - входит → диски/кабели виноваты → починить железо → E37v4;
3. Если и без дисков висит → NVRAM-стор живёт вне прошивок →
   план C: собрать «NVRAM-reset образ» (портить checksum NVAR-стора
   @0x800048+, прошить → AMI пересоздаёт стор из дефолтов образа)
   — соберу по запросу, это одна правка + пересборка.

### 16.2 Корень (zero-flash, пошаговый stage-track сборки E37v9)

| стадия | q512: запись ifr | q512: оп в пакете | согласовано? |
|---|---|---|---|

**начало** формс-пакета (сама форма 8 Б — в конец): все вопросы
формсета сдвигаются на 39, а `add_form` не делает $SPF
ifr-фиксап (в отличие от add_question/add_ref) → ~34 записи
LIVE-вопросов общей $SPF Setup DB указывают на чужие байты. TSE:
коммит значений не идёт (несохранение q600/q601 на E37v9),
страницы с битыми записями деградируют. На e16p-форме
(varstores=[]) не проявляется (дифф $SPF e32→e16p пуст) — потому
v7-состав записей не ломал. Баг зафиксирован в TODO.md (фикс:
применять fixup по резолвящимся записям с порогом точки вставки
varstore; препятствие — plan_spf_append требует страницу формы,
которой на момент form add нет).

Побочные закрытия раунда 11 (дамп-коллизии): формы 10101 в стоке
нет (глобальная коллизия form-id исключена); все 190 сток-REF

### 16.3 Раунд 11 (собран): E39 — вопросы на сток-варсторе + инвариант

Обход бага: форма e16p (varstore-free) + страница + **q600/q601 через
add_question на сток varstore 1 @95/96** (свободные байты 95..113;
прецедент NVRAM-персистентности E29/E31) + REF. Новый гейт np3
